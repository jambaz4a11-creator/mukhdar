# تطبيق المخضر الجديد (React Native + Expo + Supabase): المعمارية والخطة

> مشروع جديد ومنفصل عن نعناع. نفس فكرة توصيل الخضار والفواكه، لكن بتقنية مختلفة. هذا الملف للمحادثة الجديدة: انسخه لها أو ارفقه.
> ملاحظة: الأسعار والحدود المجانية الواردة هنا **تقديرات تتغير**، تأكد منها من مواقع Supabase وExpo وApple قبل الاعتماد.

---

## 0) رأيي المختصر بالقرارات

| القرار | رأيي |
|---|---|
| React Native + Expo | **مناسب.** تقدر تبني iOS بدون ماك عبر خدمة EAS Build السحابية، وصديقك يعرفها فيساعدك. Flutter كان ممتازاً بنعناع، لكن هنا الأفضلية لما يعرفه صديقك. |
| Supabase بدل Firebase | **مناسب لهذا المشروع.** البيانات علائقية (منتجات، طلبات، مخزون، تقارير) وPostgres أنسب من Firestore، خصوصاً للتقارير والأرباح. |
| "ما يعطل مع الاستخدام" | يتحقق بتصميم صحيح (فهارس، pagination، منطق الطلب داخل قاعدة البيانات، اختبار حمل)، مو بالتقنية وحدها. بالأسفل التفاصيل. |
| الخطة المجانية لـ Supabase | **للتطوير فقط.** للإنتاج خطة Pro (حوالي 25$ شهرياً حسب علمي، تأكد). المشاريع المجانية قد تتوقف بعد فترة عدم نشاط، وهذا ما يصلح لتطبيق فيه زبائن. |
| الدخول برقم الهاتف | يحتاج مزوّد SMS مدفوع (مثل Twilio). كلفة الرسائل وموثوقيتها بالعراق **نقطة لازم تُختبر مبكراً** (انظر القسم 8). |

**نقطة عملية:** إذا كان هذا التطبيق يُبنى لصديق ابن خالك وبفكرة نعناع، وضّح مع ابن خالك أن أفكاراً وتصاميم مشتركة بين المشروعين لا تسبب مشكلة عنده. الكود الجديد يُكتب من الصفر بتقنية مختلفة أصلاً.

## 1) نطاق المشروع (نفس نعناع)
- **تطبيق الزبون:** دخول برقم الهاتف، عنوان هرمي، تصفح المنتجات، سلة، طلب، تتبع، تقييم.
- **تطبيق السائق:** استلام طلبات بإشعار تلقائي وتحديث الحالة. **خارجي:** يبنيه مطوّر منفصل خارج هذا الـ repo ويتصل بنفس الـ backend (العقد: `docs/DRIVER-API.md`).
- **لوحة أدمن (ويب):** طلبات، منتجات، مخزون، أرباح، تقارير، موظفين.
- **Backend:** Supabase.
- **بعد المرحلة الأولى (مو الآن):** ماركت ومطاعم وتكسي وجملة غذائية. صمّم الجداول بحيث تتوسع بدون هدم (انظر القسم 6).

القرارات التجارية من نعناع تنتقل كما هي (إلا إذا صديقك يريد غيرها):
- الدفع كاش عند التسليم.
- أسعار ثابتة بدون تسعير بالوزن.
- مبالغ أعداد صحيحة بالدينار، تقريب لأقرب 250، أجرة توصيل ثابتة (1,000 بنعناع، قابلة للتعديل).
- سعر الشراء والمخزون للأدمن فقط.
- خطوة تحضير وتقييم بدل موافقة الأدمن، وإشعار السائق تلقائي.

## 2) المعمارية

```
mukhdar/
  apps/
    customer/        # Expo (React Native) + Expo Router + TypeScript
    admin/           # Next.js + Tailwind، ينشر على Vercel أو غيره
  packages/
    shared/          # أنواع TypeScript، قواعد المال والتقريب، ثوابت الحالات
  supabase/
    migrations/      # كل تغييرات قاعدة البيانات SQL
    functions/       # Edge Functions (إشعارات، مهام خلفية)
    seed.sql         # بيانات تجريبية
    tests/           # اختبارات قاعدة البيانات (pgTAP)
  docs/              # SPEC + tasks + ADR
```

**التقنيات:**
- موبايل: Expo SDK (الأحدث المستقر)، TypeScript، Expo Router، TanStack Query (تخزين مؤقت + إعادة محاولة)، Zustand للسلة.
- ويب الأدمن: Next.js + Supabase client.
- Backend: Supabase (Postgres + Auth + Storage + Realtime + Edge Functions).
- إشعارات: Expo Push Notifications.
- أخطاء ومراقبة: Sentry.
- اختبارات: Jest + React Native Testing Library، Playwright للأدمن، pgTAP لقاعدة البيانات.

## 3) كيف نضمن أنه ما يعطل مع كثرة الزبائن
هذي أهم قرارات المعمارية:

1. **الطلب يتم داخل قاعدة البيانات، مو من التطبيق.**
   دالة Postgres واحدة `place_order(...)` (security definer): تقرأ الأسعار من الجدول (مو من التطبيق)، تحسب المجموع والتقريب وأجرة التوصيل، تنقص المخزون، وتنشئ الطلب وبنوده، كل هذا بمعاملة واحدة (transaction). النتيجة: ما يصير تلاعب بالأسعار، ولا تضارب لو طلب شخصان نفس المنتج.
2. **RLS (Row Level Security) على كل جدول.** الزبون يقرأ طلباته فقط، السائق الطلبات المعيّنة له، والأدمن الكل. جدول `product_costs` (سعر الشراء) للأدمن فقط.
3. **فهارس مدروسة:** على `orders(customer_id, created_at desc)` و`orders(status, created_at)` و`products(category_id, is_active)` وغيرها. تُراجع بـ `EXPLAIN` قبل الإطلاق.
4. **Pagination دائماً:** لا قائمة بلا حد (طلبات، منتجات). نحمّل 20 إلى 50 سجل بالمرة.
5. **Realtime بحدود:** الزبون يتابع **طلبه الحالي فقط**، مو كل جدول الطلبات. اشتراكات Realtime لها حدود حسب الخطة.
6. **تخزين مؤقت بالتطبيق:** كتالوج المنتجات يُخزَّن (TanStack Query + تخزين محلي)، فالتطبيق يفتح بسرعة ويتحمل ضعف الشبكة. إعادة محاولة تلقائية للطلبات الفاشلة.
7. **صور خفيفة:** تُصغَّر قبل الرفع (أو أحجام جاهزة). صورة 5MB لمنتج هي أول سبب لبطء التطبيق.
8. **التقارير من جداول مُجمّعة:** جدول `daily_stats` يتحدث بـ trigger أو دالة، فاللوحة ما تمسح كل الطلبات كل مرة (نفس فكرة `dailyStats` بنعناع).
9. **Connection pooling:** استخدم رابط الـ pooler الخاص بـ Supabase من Edge Functions والأدمن.
10. **اختبار حمل قبل الإطلاق:** سكربت k6 يحاكي مئات الطلبات المتزامنة على `place_order` ويقيس الزمن والأخطاء.
11. **حجم الحاسوب:** إذا ظهر ضغط، ارفع حجم Compute بالخطة. هذا إعداد، مو إعادة بناء.
12. **نسخ احتياطي:** فعّل النسخ الاحتياطي اليومي (متوفر بالخطط المدفوعة، تأكد من مدة الاحتفاظ). وجرّب استعادة نسخة مرة واحدة قبل الإطلاق.
13. **تنبيهات:** Sentry للتطبيق، وتنبيه عندما يقترب استخدام قاعدة البيانات من الحد.

## 4) تصميم قاعدة البيانات (مسودة، تتحسن بمرحلة الـ SPEC)

- `profiles` (id = auth.users.id، role: customer|driver|admin|staff، phone، name)
- `sectors`، `subsections`، `buildings` (رقم، subsection_id)، والشقة تُكتب نصاً بالطلب. هيكل العنوان: **قطاع ← قسم فرعي ← بناية ← شقة** (أرقام البلوكات تتجاوز 650؛ المالك يعدّل القوائم من الأدمن).
- `addresses` (customer_id، building_id، apartment، ملاحظة)
- `categories`، `products` (name، price_iqd bigint، unit، image_path، is_active، sort_order)
- `product_costs` (product_id، cost_iqd): **admin only**
- `inventory_movements` (product_id، qty، type: purchase|sale|waste|adjust، created_at) والرصيد يُحسب منها أو من جدول `stock`
- `orders` (customer_id، address_id، status، subtotal، delivery_fee، total، driver_id، created_at...)
- `order_items` (order_id، product_id، name_snapshot، price_snapshot، qty)
- `ratings` (order_id، stars، comment)
- `push_tokens` (user_id، token، platform)
- `daily_stats`
- جاهز للتوسع: حقل `city_id` و`vendor_id` (nullable الآن) حتى تضيف ماركت ومطاعم لاحقاً بدون هدم.

**حالات الطلب:** `pending` ← `preparing` ← `out_for_delivery` ← `delivered` (أو `cancelled`). التحويلات الصحيحة تُفرض داخل قاعدة البيانات، مو بالتطبيق.

**الأدوار:** تُخزَّن بـ `profiles.role` وتُقرأ بسياسات RLS. لا تثق أبداً بدور مرسل من التطبيق.

## 5) نشر iOS بدون ماك (بـ Expo + EAS)

**المتطلبات:**
- حساب **Apple Developer** (حوالي 99$ سنوياً). هذا ما ينتجنب. لازم باسم صاحب المشروع (صديقك أو ابن خالك).
- حساب Expo مجاني وEAS CLI.
- حساب **Google Play** (حوالي 25$ مرة واحدة) للأندرويد.

**الخطوات (من ويندوز):**
1. `npm install -g eas-cli` ثم `eas login`.
2. بالمشروع: `eas build:configure`.
3. `eas build -p ios`: يسألك عن حساب Apple، ويدير الشهادات وملفات التوقيع **تلقائياً**. البناء يتم على سيرفرات Expo (macOS) مو على جهازك.
4. `eas submit -p ios`: يرفع التطبيق إلى App Store Connect.
5. من App Store Connect تفعّل **TestFlight** للتجربة على آيفون حقيقي، وبعدها ترسل للمراجعة.
6. نفس الشي للأندرويد: `eas build -p android` ثم `eas submit -p android`.

**ملاحظات مهمة:**
- أثناء التطوير تجرّب على آيفون بتطبيق **Expo Go** (مسح QR)، لكنه ما يدعم كل المكتبات الأصلية. إذا احتجت مكتبة خاصة، استخدم **development build**.
- خطة EAS المجانية لها عدد محدود من البناءات الشهرية وطابور أبطأ (تأكد من الحدود الحالية). غالباً تكفي بالتطوير.
- التدقيق من Apple صارم: لازم سياسة خصوصية، ووصف واضح، وحساب تجريبي للمراجعين، وحذف الحساب من داخل التطبيق (مطلوب من Apple). صمّم هذا من البداية.
- الإشعارات على iOS تحتاج إعداد APNs (EAS يساعد بالمفتاح).

## 6) التوسع المستقبلي (ماركت، مطاعم، تكسي، جملة)
- **لا تبنيها الآن.** فقط لا تقفل الباب: `vendor_id` و`city_id` nullable، وجدول `products` يقبل أنواع مختلفة.
- **التكسي** مشروع مستقل بحجمه (تتبع مباشر، أجرة، مطابقة، خرائط بفاتورة). خله مرحلة ثانية بسعر منفصل.
- **الجملة الغذائية** تحتاج غالباً أسعاراً مختلفة (أسعار جملة، حد أدنى للكمية). خله نوع حساب أو قائمة أسعار لاحقاً.

## 7) المراحل (للتنفيذ بـ Claude Code)
1. **SPEC:** كتابة المواصفات (SPEC-backend، SPEC-customer، SPEC-driver، SPEC-admin) وملف `tasks/`.
2. **Backend:** المخطط والـ RLS ودوال Postgres (`place_order` وغيرها) مع اختبارات pgTAP. التشغيل المحلي بـ `supabase start` (يحتاج Docker على ويندوز).
3. **تطبيق الزبون:** Expo + شاشات التصميم.
4. **لوحة الأدمن.**
5. **الإشعارات التلقائية** (تطبيق السائق خارجي: مطوّر منفصل، عبر `docs/DRIVER-API.md`).
6. **بيانات تجريبية** (على طريقة `seed:demo` بنعناع).
7. **اختبار حمل ومراجعة أمان (RLS) وقائمة ما قبل الإطلاق.**
8. **نشر:** Supabase Pro، EAS Build، TestFlight، المتاجر.

**ملاحظة للجهاز:** على ويندوز، Supabase المحلي يحتاج Docker Desktop وهو يستهلك RAM وقرصاً. بعد ما عانيت من امتلاء القرص بنعناع، فكّر باستخدام مشروع Supabase سحابي مجاني للتطوير بدل Docker، أو شغّل المرحلة 2 في جلسة سحابية.

## 8) نقاط خطرة لازم تُحسم مبكراً
1. **رسائل OTP بالعراق:** اختبر مزوّد SMS فعلياً (وصول الرسائل، التأخير، الكلفة) قبل بناء كل شي عليه. إذا فشل، فكّر ببدائل (واتساب أو مزوّد محلي).
2. **ملكية الحسابات:** Supabase وApple وGoogle Play والنطاق كلها باسم صاحب المشروع.
3. **الكلف الشهرية:** Supabase Pro، رسائل SMS، (ربما EAS مدفوع)، النطاق. اجمعها واعرفها قبل ما تعطي سعراً.
4. **سياسة الخصوصية وحذف الحساب** مطلوبة لـ Apple وGoogle.
5. **التصميم:** ملف تصميم المخضر (khudarna) موجود. صوّر شاشات التطبيق للمحادثة الجديدة.

## 9) أول prompt للجلسة الجديدة (الصقه بـ Claude Code)

> نص تاريخي: الـ prompt الأصلي كما استُخدم لبدء المشروع. تغيّر بعده: تطبيق السائق صار **خارجياً** (مطوّر منفصل، `docs/DRIVER-API.md`).

```

التقنيات: React Native + Expo (TypeScript, Expo Router) لتطبيقي الزبون والسائق، Next.js للوحة الأدمن، Supabase كـ backend (Postgres + RLS + Auth برقم الهاتف + Storage + Edge Functions). Monorepo كما في docs/ARCHITECTURE.md.

المرحلة 1 فقط الآن: اكتب المواصفات ولا تبنِ كوداً.
- SPEC-backend.md و SPEC-customer.md و SPEC-driver.md و SPEC-admin.md.
- مخطط قاعدة البيانات (SQL) مع سياسات RLS، ودالة place_order التي تحسب الأسعار والمجموع داخل قاعدة البيانات وتنقص المخزون بمعاملة واحدة.
- tasks/*.md: مهمة صغيرة لكل ملف، مرتبة، ولكل مهمة اختبارات.
- قواعد ثابتة: مبالغ أعداد صحيحة بالدينار، تقريب لأقرب 250، أجرة توصيل قابلة للتعديل، سعر الشراء والمخزون للأدمن فقط، الدفع كاش، أسعار ثابتة، عنوان هرمي (قطاع ← قسم فرعي ← بناية ← شقة)، حالات الطلب pending/preparing/out_for_delivery/delivered/cancelled، إشعار السائق تلقائي، تقييم بعد التسليم.
- اضف قسم "كيف نضمن الأداء" يشمل الفهارس وpagination واختبار حمل k6.
- اكتب أي قرار غير محدد كـ "افتراضات" بنهاية الملف، ولا تسألني.

ثم commit وتوقف.
```

بعدها نراجع الـ SPEC قبل ما ننتقل للبناء.
