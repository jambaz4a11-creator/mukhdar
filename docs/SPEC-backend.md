# SPEC-backend: المخضر (Supabase)

> المرجع التنفيذي: كل ملفات `supabase/migrations/` بالترتيب (الأساس `20261110000001_init.sql`، ثم storage، ثم إصلاحات Advisor، ثم إصلاحات مراجعة T01–T05). هذا الملف يشرح **لماذا** و**ماذا**؛ الـ SQL هو المصدر الوحيد للحقيقة عند التعارض.
> الحالة: مطبّق على `mukhdar-dev` (Supabase، Postgres 17)، ومغطى باختبارات pgTAP بـ `supabase/tests/` (تعمل على السحابة وفي CI على Supabase محلي). عقد تطبيق السائق (`apps/driver`، داخل هذا الـ repo): `docs/DRIVER-API.md` وSPEC-driver.

## 1) الهدف والنطاق
- خلفية واحدة لثلاث واجهات، كلها داخل هذا الـ repo: تطبيق الزبون (`apps/customer`)، لوحة الأدمن (`apps/admin`، ويب)، وتطبيق السائق (`apps/driver`، SPEC-driver؛ عقد الدوال `docs/DRIVER-API.md`). المطوّر الخارجي أُلغي (قرار المالك 2026-11-19).
- مدينة واحدة (بسماية) بالمرحلة الأولى، مع حقول `city_id` و`vendor_id` (nullable) للتوسع.
- لا خادم خاص: كل المنطق الحساس داخل Postgres (دوال `security definer`) وكل القراءة عبر RLS.

## 2) القواعد الثابتة
| القاعدة | التطبيق بقاعدة البيانات |
|---|---|
| المبالغ أعداد صحيحة بالدينار | كل الأعمدة `bigint` بلاحقة `_iqd` |
| تقريب لأقرب 250 | `round_iqd()`؛ وسعر المنتج وأجرة التوصيل **يجب** أن تكون مضاعفات 250 (قيد CHECK) |
| أجرة توصيل قابلة للتعديل | `app_settings.delivery_fee_iqd` (افتراضي 1000)، وتُنسخ للطلب لحظة إنشائه |
| أسعار ثابتة، بدون وزن | `qty` عدد صحيح 1..99 لكل بند، بوحدة البيع `products.unit`: الخضار والفواكه `نص كيلو` (السعر لكل نص كيلو، و`qty = 3` = كيلو ونص)، الأعشاب `باقة`، وما يُباع بالقطعة `حبة`/`علبة`/`قنينة`/`سلة`. سعر ثابت لكل وحدة، لا وزن فعلي ولا كسور. المخزون بنفس الوحدة |
| سعر الشراء والمخزون للأدمن فقط | `product_costs`، `stock`، `inventory_movements`، `order_item_costs`، `daily_stats` محمية بـ RLS. الزبون يرى `products.in_stock` فقط |
| الدفع كاش عند التسليم | لا جداول دفع. `total_iqd` هو ما يستلمه السائق |
| إشعار السائق تلقائي | `place_order` يبلّغ الأدمن والموظفين فقط؛ عند `ready` يكتب `set_order_status` إشعاراً لكل السائقين النشطين (طلب متاح) وللزبون |
| تقييم بعد التسليم | `rate_order()` يقبل فقط طلباً `delivered` لنفس الزبون، مرة واحدة |
| المبيعات وصافي الربح (قرار 2026-11-15، يُبنى بـ T18/T20) | المبيعات = `subtotal` للطلبات المسلّمة (بدون الأجرة، للسواق) بتاريخ `delivered_at`. صافي الربح = الربح الإجمالي − كلفة الهدر − كلفة تسويات الجرد السالبة، بكلفة الوحدة المحفوظة على كل حركة (§12) |
| كتابة المال عبر دوال | المنتجات والأسعار وسعر الشراء والإعدادات تُكتب بدوال فقط (§12، T18/T19)؛ لا insert/update مباشر من المتصفح |

## 3) الأدوار
`customer` (افتراضي عند التسجيل) · `driver` · `staff` · `admin`.
- الدور يُخزَّن في `profiles.role` ولا يتغير إلا عبر `set_user_role()` (أدمن فقط).
- العمود محمي بصلاحيات على مستوى العمود: المستخدم يعدّل `full_name` فقط.
- الأدمن لا يقدر يخفّض دوره أو يعطّل نفسه (`CANNOT_DEMOTE_SELF`)، ولا يُزال آخر أدمن نشط (`LAST_ADMIN`).
- حساب معطّل (`is_active = false`) يُعامل كأنه بلا دور.
- **رمز مؤقت (`profiles.must_change_pin`، migration `20261123000001`):** يُضبط بعد `admin-create-user` و`admin-reset-pin` (داخل `finish_user_creation` و`record_pin_reset`)، ويُمسح تلقائياً حين تتغير كلمة السر فعلاً (trigger `on_auth_user_password_changed` على `auth.users.encrypted_password`؛ استدعاء من التطبيق لا يمسحه). أثناءه `current_user_role()` = null: كل دالة وسياسة مبنية على الدور ترفض كأن الحساب بلا دور، و`place_order` ترفض `PIN_CHANGE_REQUIRED`. يبقى: قراءة الملف الشخصي (لمعرفة العلامة)، صفوف الزبون نفسه، تغيير الرمز (GoTrue `updateUser`)، وحذف الحساب. **افتراض:** تغيير الرمز لنفس الرمز المؤقت يمسح العلامة أيضاً (الـ hash يتغير مع كل ملح)؛ التطبيقات ترفض الجديد = الحالي.
- **المصادقة الثنائية للأدمن والموظف (T23 C1، قرار المالك 2026-11-17، migration `20261130000001`):** `private.current_user_role()` يرجع `admin`/`staff` **فقط بجلسة `aal2`** (الـ PIN + رمز TOTP من تطبيق مصادقة؛ claim `aal` بالـ JWT). بالـ PIN وحده (`aal1`) أو برمز بلا claim، الأدمن والموظف بلا دور: كل دالة إدارية ترفض (`NOT_ALLOWED`، أو `NOT_AUTHENTICATED` من `set_order_status`) وكل سياسة RLS مبنية على الدور تخفي الصفوف؛ يبقى ملفه الشخصي (للتوجيه لصفحة `/mfa`) والتسجيل/التحقق عبر GoTrue. **الزبون والسائق بلا تغيير** (aal1 يكفي). الدالتان `admin-reset-pin`/`admin-create-user` تطلبان aal2 أيضاً (`MFA_REQUIRED`، §8). الاسترجاع: `admin_reset_mfa(p_user_id) → int` (أدمن aal2) يحذف عوامل حساب غير أدمن ويبطل جلساته ويُسجَّل بـ `admin_audit` (`mfa_reset`، `before.factors`، `after.via = 'panel'`)؛ `ADMIN_ACCOUNT` لهدف أدمن أو للمستدعي نفسه، `USER_NOT_FOUND`. مصادقة الأدمن تُعاد فقط بسكربت الطوارئ (`break_glass_reset_mfa(p_user_id)`، service_role، أدمن فقط وإلا `INVALID_REQUEST`؛ `actor` null و`via = 'break_glass'`). `admin_audit.action` يقبل `mfa_reset`.

## 5) دوال RPC (الواجهة الوحيدة للكتابة الحساسة)
كل الأخطاء ترجع بـ `message` ثابت (رمز إنجليزي) يترجمه التطبيق لرسالة عربية. `detail` يحمل `product_id` عند أخطاء المنتجات.

### `place_order(p_address_id, p_items, p_idempotency_key, p_note?) → jsonb`
- `p_items`: `[{"product_id": uuid, "qty": int}]`. **التطبيق لا يرسل أي سعر.**
- الخطوات بمعاملة واحدة:
  1. يتحقق أن المستخدم زبون نشط (ورمزه غير مؤقت) وله رقم هاتف.
  2. **منع التكرار:** قفل استشاري لكل زبون. لو وُجد طلب بنفس المفتاح يرجعه مع `replayed: true`. التطبيق يولّد المفتاح مرة لكل محاولة "تأكيد الطلب" ويعيد استخدامه عند إعادة المحاولة.
  3. **حد الطلبات المفتوحة:** يرفض إن كان للزبون `max_active_orders` (افتراضي 3) طلبات غير منتهية (`pending`/`preparing`/`ready`/`out_for_delivery`).
  4. المتجر مفتوح؟ العنوان للزبون نفسه؟ والعمارة والوحدة والقطاع مفعّلة؟
  5. يتحقق من صيغة البنود **قبل أي تحويل نوع** (كل بند كائن، `product_id` نص UUID، `qty` عدد صحيح)، ثم يدمج المكرر، ويرفض كمية خارج 1..99 (`INVALID_QTY`) أو أكثر من 50 عنصراً خاماً (`TOO_MANY_ITEMS`)؛ **بعد الدمج (T23 H2):** أكثر من `app_settings.max_order_lines` منتجاً (افتراضي 30) ← `TOO_MANY_ITEMS`، وكمية منتج أكثر من `app_settings.max_line_qty` وحدة بيع (افتراضي 20 = 10 كيلو للنص كيلو) ← `QTY_LIMIT`؛ و`detail` = الحد في الحالات الثلاث.
  6. **يقفل صفوف `stock` بترتيب `product_id`** (يمنع بيع نفس الحبة مرتين ويمنع الـ deadlock).
  7. يتحقق من التفعيل والرصيد، يحسب `subtotal = round_iqd(Σ price × qty)`، يتحقق من الحد الأدنى، ثم `total = subtotal + delivery_fee`.
  8. ينشئ الطلب والبنود وتكاليفها، ينقص المخزون، يسجل الحركات والتاريخ، ويضيف إشعاراً واحداً للأدمن والموظفين (`audience = 'admins'`، النص: الوحدة والعمارة والمجموع). السائقون لا يُبلَّغون هنا.
- يرجع: `{order_id, order_number, total_iqd, status, replayed}`.
- أخطاء: `NOT_AUTHENTICATED`, `NOT_CUSTOMER`, `PIN_CHANGE_REQUIRED` (رمز مؤقت، §3), `PHONE_REQUIRED`, `IDEMPOTENCY_KEY_REQUIRED`, `TOO_MANY_ACTIVE_ORDERS` (`detail` = الحد الساري: للحساب الجديد `new_account_max_active_orders`), `STORE_CLOSED`, `ADDRESS_NOT_FOUND`, `ADDRESS_INACTIVE`, `EMPTY_CART`, `TOO_MANY_ITEMS` (`detail` = الحد، T23 H2), `QTY_LIMIT` (`detail` = الحد، T23 H2), `INVALID_QTY` (يشمل بنداً ليس كائناً أو `qty` ليس عدداً صحيحاً), `PRODUCT_UNAVAILABLE` (يشمل `product_id` مفقوداً أو بصيغة خاطئة؛ `detail` = القيمة المرسلة), `INSUFFICIENT_STOCK`, `BELOW_MIN_ORDER`.

### `set_order_status(p_order_id, p_status, p_reason?, p_return_stock = true) → orders`
مخطط الحالات:
```
pending ──► preparing ──► ready ──► out_for_delivery ──► delivered
   │            │           │              │
   └────────────┴───────────┴──────────────┴──► cancelled
```
| الدور | المسموح |
|---|---|
| admin | أي تحويل صحيح (ومنه الإلغاء من `out_for_delivery`، للأدمن وحده) |
| staff | ← `preparing`، ← `ready`، ← `out_for_delivery` (يتطلب سائقاً معيَّناً)، ← `delivered`؛ والإلغاء من `pending`/`preparing`/`ready`. آخر تحويلين **احتياطيان** (migration `20261120000001`، 2026-11-16) حين يكون تطبيق السائق معطّلاً أو نسي السائق |
| driver (المعيَّن فقط) | `ready` ← `out_for_delivery` (يتطلب أن يكون معيَّناً)، `out_for_delivery` ← `delivered` |
| customer (صاحب الطلب) | الإلغاء وهو `pending` فقط |

آثار جانبية: طوابع الوقت (`preparing_at`، `ready_at`، ...)، سجل التاريخ، إشعار للزبون (قيد التحضير، "طلبك جاهز، بانتظار السائق"، بالطريق، تم التوصيل، الإلغاء). عند `ready`: إن لم يكن للطلب سائق ← إشعار `audience = 'drivers'` لكل السائقين النشطين (`type: new_order`)؛ وإن عُيِّن مسبقاً أثناء التحضير ← إشعار لسائقه فقط (`type: ready`). `p_reason` يُقص لـ 300 حرف. الإلغاء **يرجع المخزون** بحركة `cancel_return`، ويُبلّغ السائق المعيَّن (إن وُجد) بإشعار `type: cancelled` نصه **البلوك والبناية فقط** (`بلوك X - بناية Y`؛ R3 M1، migration `20261211000001`: سبب الإلغاء الحر لا يُرسل بالإشعار لأنه قد يحوي هاتف الزبون أو طابقه أو شقته، ويبقى بالطلب وسجل الحالات). **الإلغاء بلا إرجاع** (`p_return_stock = false`، قرار المالك 2026-11-16): للأدمن وحده ولطلب `out_for_delivery` وحده (البضاعة طلعت مع السائق؛ غير ذلك `INVALID_REQUEST` بـ `detail = 'p_return_stock'`، وغير الأدمن `NOT_ALLOWED`): الرصيد لا يتغير، وتُكتب حركتان بنفس الكمية لكل منتج: `cancel_return` (+) و`waste` (−) بملاحظة "cancelled after dispatch" وكلفة البنود وقت الطلب (`order_item_costs`)، فيبقى السجل = الرصيد ويدخل الهدر خسائر اليوم وصافي الربح. التسليم يحدّث `daily_stats` (الإيراد، الأجرة، التكلفة من `order_item_costs`، الربح الإجمالي).
أخطاء: `ORDER_NOT_FOUND`, `INVALID_TRANSITION`, `NOT_ALLOWED`, `NO_DRIVER_ASSIGNED`.

### دوال السائق
- `available_orders(p_limit=20)`: الطلبات غير المعيَّنة بحالة `ready` فقط **بدون هاتف الزبون واسمه وطابقه وشقته**، حد أقصى 50. `item_count` = مجموع الكميات بوحدات البيع، و`line_count` = عدد البنود المختلفة ("N منتجات" بتطبيق السائق؛ T27 D13، migration `20261208000001`). لغير السائق النشط: `NOT_ALLOWED`.
- `accept_order(p_order_id)`: على طلب `ready` غير معيَّن فقط (غير ذلك `ORDER_NOT_AVAILABLE`). أول سائق يقبل يأخذ الطلب؛ الثاني يحصل `ORDER_NOT_AVAILABLE`. بعد القبول يرى السائق الهاتف والعنوان الكامل عبر RLS. **قفل الصف (migration `20261125000001`، جلسة C M1):** صف السائق يُقفل `for share` بشرط `role = 'driver' and is_active and not must_change_pin` (لا قبل القفل فقط): سائق خُفّض أو عُطّل أو أُعيد ضبط رمزه أثناء انتظار القفل يُرفض `NOT_ALLOWED` ولا يأخذ الطلب.
- `assign_driver(p_order_id, p_driver_id)` (موظف/أدمن): تعيين أو تغيير يدوي من `preparing` أو `ready`، أو **نقل طلب `out_for_delivery` لسائق نشط آخر** (قرار المالك 2026-11-16؛ الموظف أيضاً كإجراءات التوصيل الاحتياطية؛ الحالة لا تتغير، ملاحظة التاريخ `driver_reassigned`)، مع إشعار للسائق (`type: assigned`)، وإشعار السائق السابق عند التغيير (`type: unassigned`). كل تغيير من سائق لآخر يُسجَّل بـ `admin_audit` (`order_driver`). ملف السائق يُقفل `for share` (يتسلسل مع تعطيله وتخفيضه). **جلسة C:** سائق `must_change_pin` لا يُسند له (`DRIVER_PIN_PENDING`: لا يقرأ الطلب بـ RLS ولا يستلم إشعاراً)؛ التعيين لنفس السائق الحالي لا يفعل شيئاً (لا سجل ولا إشعار ولا تدقيق). أخطاء: `NOT_ALLOWED`, `DRIVER_NOT_FOUND` (ليس سائقاً نشطاً), `DRIVER_PIN_PENDING` (سائق لم يغيّر رمزه المؤقت), `ORDER_NOT_AVAILABLE` (الطلب ليس `preparing`/`ready`/`out_for_delivery`، أو غير موجود).
- `list_drivers()` (موظف/أدمن): السائقون فقط، بالأعمدة `id, full_name, phone, is_active, must_change_pin` (جلسة C: العلامة لتعطّل اللوحة صف من لم يغيّر رمزه بنافذة التعيين؛ لقائمة التعيين واسم السائق بجدول الطلبات). غيرهم: `NOT_ALLOWED`.

### طلبات تسجيل السواق (T27، SPEC-driver §3 و§4.1، migration `20261208000001`)
السائق يسجّل من `apps/driver` بلا أي حساب؛ الأدمن يتصل بالرقم ثم يوافق؛ الجهاز نفسه (من يملك **سر الجهاز**: 32 بايت base64url بلا حشو = 43 محرفاً، ويخزّن الخادم SHA-256 (hex) لنصه فقط) يختار رمزه، وEdge Function تنشئ الحساب. كل الدوال SECURITY DEFINER بـ `search_path = ''`.
- `driver_request_rate_hit(p_ip, p_phone) → boolean` (**service_role**): نفس تصميم `signup_rate_hit` (مفاتيح sha256، كل محاولة تُحسب): 10/ساعة لكل IP، 3/24 ساعة لكل رقم؛ `p_phone` null = الـ IP فقط.
- `submit_driver_request(p_phone, p_full_name, p_secret_hash, p_push_token) → uuid` (**service_role**، `driver-register`): الرقم `9647XXXXXXXXX` (وإلا `PHONE_INVALID`)، الاسم بعد `clean_user_text` 2..80 (وإلا `NAME_INVALID`)، الـ hash 64 hex (وإلا `INVALID_REQUEST`)، رمز الإشعار بصيغة Expo وإلا يُتجاهل. قفل استشاري لكل رقم؛ رقم له حساب ← `PHONE_TAKEN`؛ طلب مفتوح لنفس الرقم: بنفس الـ hash ← نفس `id` (إعادة إرسال آمنة، بلا إشعار جديد)، بغيره ← `REQUEST_EXISTS`، وموافقة منتهية تُستبدل بالطلب الجديد؛ 50 طلباً معلّقاً ← `TOO_MANY_PENDING`. يكتب إشعار `admins_only` **عام** "طلب سائق جديد، افتح طلبات السواق" بلا الاسم (R1 M4؛ `data.type = 'driver_request'`). الموافقة المنتهية تبقى سجلاً بحالة `rejected` وملاحظة "انتهت مدة الموافقة وسُجّل طلب جديد" بدل حذفها (R1 L5).
- `driver_request_status(p_request_id, p_device_secret) → text` (**`anon` و`authenticated`**: الجهاز بلا حساب، بالمفتاح المنشور): `pending`/`approved`/`rejected`/`expired`/`completed`، أو `not_found` لأي عدم تطابق (معرّف، سر، طول السر، null). لا بيانات أخرى. الدالة الوحيدة الـ SECURITY DEFINER المكشوفة لـ `anon` (تحذير Advisor متوقع؛ §6 البند 6).
- `list_driver_requests(p_status = 'pending', p_limit = 50)` (أدمن aal2): `id, full_name, phone, status, created_at, decided_at, decided_by_name, decision_note`؛ `pending` الأقدم أولاً، `decided` آخر 30 يوماً الأحدث أولاً (والحالة `expired` محسوبة). `p_limit` 1..200. أخطاء: `NOT_ALLOWED`، `INVALID_REQUEST` (فلتر غير معروف).
- `decide_driver_request(p_id, p_approve, p_note = null) → text` (أدمن aal2): الموافقة من `pending` فقط؛ الرفض من `pending` أو من `approved` (**سحب الموافقة**، سارية أو منتهية، R1 M1: `rejected` ومسح رمز الإشعار و`approved_until`، و`before.status = 'approved'` بالتدقيق)؛ المكتمل والمرفوض وإعادة الموافقة ← `REQUEST_ALREADY_DECIDED` (`detail` = الحالة)؛ `REQUEST_NOT_FOUND`؛ الموافقة على رقم صار له حساب ← `PHONE_TAKEN` (يبقى معلّقاً). الموافقة: `approved_until = now() + 7 days` وإشعار `driver_request` للجهاز إن كان له رمز ("وافق المحل على طلبك"، `data = {type: 'driver_request_approved', request_id}`). الرفض: يمسح رمز الإشعار. الملاحظة تُنظَّف و≤ 300 (وإلا `INVALID_REQUEST`). سطر `admin_audit` (`driver_request`، `before = {status}`، `after = {status, note, phone}`). يرجع الحالة الجديدة. أخطاء أخرى: `NOT_ALLOWED`.
- `begin_driver_completion(p_request_id, p_secret_hash) → (phone, full_name)` (**service_role**، `driver-complete-registration`): قفل الصف؛ hash لا يطابق أو غير موجود ← `REQUEST_NOT_FOUND`؛ ليس `approved` ← `REQUEST_NOT_APPROVED` (`detail` = الحالة)؛ موافقة منتهية ← `REQUEST_EXPIRED`.
- `finish_driver_registration(p_request_id, p_user_id)` (**service_role**، بعد `auth.admin.createUser`): بمعاملة واحدة وشرطياً على `approved` (وإلا `REQUEST_NOT_APPROVED`؛ وغير موجود `REQUEST_NOT_FOUND`؛ وموافقة انتهت أثناء الإكمال `REQUEST_EXPIRED`، R1 L1)؛ الحساب يجب أن يكون برقم الطلب نفسه (`USER_NOT_FOUND`، `INVALID_REQUEST`)؛ الملف الشخصي ← `driver`، الاسم، `is_active`، بلا `must_change_pin`؛ الطلب ← `completed` مع `user_id` و`completed_at` ومسح رمز الإشعار.
- `claim_push_notifications` يحلّ جمهور `driver_request` إلى `driver_requests.push_token` (مزوّد `expo`، `platform = 'unknown'`) **فقط** لطلب ما زال `approved` وغير منتهٍ؛ شكل المخرجات لم يتغير (`push-dispatch` بلا تغيير). الرمز الميت لا يُحذف من الطلب (أفضل جهد؛ الاستطلاع كل 30 ثانية هو الضمان).
- `pending_driver_requests_count() → integer` (أدمن aal2، R1 L8، migration `20261209000001`): عدد الطلبات المعلّقة لشارة اللوحة، بلا أسماء وأرقام. غير الأدمن ← `NOT_ALLOWED`.
- **`set_user_role` وزبون ← سائق (R1 H1، 2026-11-20):** ترقية زبون إلى سائق تتطلب `must_change_pin` (إعادة ضبط رمزه من الأدمن أولاً بعد مكالمة)، وإلا `PIN_RESET_REQUIRED`؛ كالموظف والأدمن. السبب: تسجيل الزبون بلا تحقق من الهاتف، فمن يحمل الرمز قد لا يملك الرقم. السائق الجديد يغيّر الرمز المؤقت عند أول دخول (الحارس).
- التنظيف اليومي (`purge_push_history`): حذف الطلبات `rejected`/`completed`/الموافقة المنتهية بعد 30 يوماً من آخر تغيير، وصفوف حد المعدل الأقدم من يوم.

- `adjust_stock_bulk(p_items, p_type, p_note?) → int` (أدمن): `[{product_id, qty, unit_cost_iqd?}]` (حتى 500، بلا تكرار) بمعاملة واحدة وأقفال `stock` بترتيب `product_id`؛ أي بند خاطئ يُفشل الكل. لهدر اليوم والمشتريات بالجملة. نفس أخطاء `adjust_stock`.

## 6) الأمان
1. RLS مفعّل على **كل** جدول. `notification_outbox` بلا سياسات (service_role فقط).
2. الصلاحيات تُسحب بالكامل ثم تُمنح صراحة لكل جدول ولكل دالة (`revoke all` + `grant`)، حتى لا تتسرب صلاحيات Supabase الافتراضية.
3. لا سياسات `insert/update/delete` على الطلبات والمخزون؛ الكتابة فقط من خلال الدوال.
4. الدوال `security definer` مع `set search_path = public, pg_temp`. دوال الأدوار المستخدمة داخل RLS (`current_user_role`، `is_admin`، `is_staff_or_admin`) تعيش بمخطط `private` غير المكشوف بالـ API، والأسماء بـ `public` أغلفة security invoker. كل الدوال لها `search_path` ثابت.
5. مفتاح `service_role` يُستخدم **فقط** داخل Edge Functions، ولا يوضع أبداً بتطبيق موبايل أو بكود الويب في المتصفح.
6. `anon` يقرأ الكتالوج والعناوين والإعدادات فقط (التصفح قبل الدخول)، وينفّذ دالة SECURITY DEFINER واحدة فقط: `driver_request_status` (T27: جهاز السائق قبل أن يكون له حساب؛ تحذير Advisor متوقع وموثَّق، والحماية سر 256 بت).
7. السياسات تستخدم `(select auth.uid())` و`(select private.is_admin())` (تُحسب مرة لكل استعلام)، ولا توجد سياستان permissive لنفس الدور والعملية. الهدف: Advisor بلا تحذيرات عدا دوال RPC العشر المقصودة.
8. الدوال الجديدة **لا تُنفَّذ افتراضياً** من `PUBLIC` (`alter default privileges for role postgres` عامة، لا بالمخطط)، فكل دالة RPC جديدة تحتاج `grant execute` صريحاً.
9. `service_role` (لـ Edge Functions فقط) له صلاحيات محددة: `usage` على `public`، `select/update` على `notification_outbox`، `select/delete` على `push_tokens`، `select` على `profiles` و`orders`، وتنفيذ `signup_rate_hit` (جدوله بمخطط `private`) و`revoke_user_sessions` ودوال T19 (`admin_rate_hit`، `record_pin_reset`، `finish_user_creation`؛ لا صلاحية مباشرة على `pin_resets`/`user_creations`)، ودوال طلبات السواق (T27: `driver_request_rate_hit`، `submit_driver_request`، `begin_driver_completion`، `finish_driver_registration`؛ لا صلاحية على جدول `driver_requests` نفسه). أي حاجة جديدة تُمنح بـ migration المهمة. `01_schema.sql` يفحص القائمة بالضبط (محلياً وبالسحابة).
10. الكتابة المباشرة على `products` و`addresses` بأعمدة محددة فقط (لا `in_stock` ولا `id` ولا `created_at`، ولا نقل عنوان لزبون آخر). لا صلاحيات على الـ sequences لـ `anon`/`authenticated`.
11. bucket الصور عام (العرض بالرابط العام)، لكن **قائمة الملفات** للأدمن فقط.

## 7) المصادقة (الهاتف + PIN، بدون رسائل)
> قرار المالك 2026-11-14: لا SMS ولا OTP (كلفة الرسائل بالعراق). التفاصيل والأسباب: [ADR 0001](ADR/0001-phone-pin-auth.md).
- Supabase Auth بمزوّد **Phone مع كلمة سر**: كلمة السر = رمز **PIN من 6 أرقام**. تأكيد الهاتف **معطّل**. **لا تُرسل أي رسالة أبداً** (لا SMS ولا بريد).
- **التسجيل عبر الخادم فقط (قرار المالك 2026-11-15):** التسجيل العام بـ GoTrue **مطفأ** (Allow new users to sign up: OFF)، فلا `signUp` ولا `signInWithOtp` ينشئ حساباً. الحساب الجديد من Edge Function `signup` (§8): تفحص الرقم والـ PIN بالخادم بنفس قواعد `packages/shared`، وتنشئه بـ `auth.admin.createUser` (هاتف مؤكد)، بحدود معدل خاصة (20/ساعة لكل IP، 5/ساعة لكل رقم؛ `private.signup_rate_limits`، migration `20261117000001`). ثم يدخل التطبيق بـ `signInWithPassword`.
- **Send SMS Hook** (`private.hook_send_sms_reject`، migration `20261116000001`) يرفض كل إرسال: `signInWithOtp` وإعادة الإرسال وتغيير الرقم و`reauthenticate` تفشل. الكلفة صفر حتى لو ضُبط مزوّد SMS بالخطأ. (`signInWithOtp` لرقم جديد كان يُنشئ الحساب قبل رفض الإرسال؛ أُغلق بإطفاء التسجيل العام، افتراض 53.)
- صيغة الرقم E.164: `+9647XXXXXXXXX`. التطبيقات تقبل `07XXXXXXXXX` (وأرقاماً عربية) وتحوّله (`phonePinCredentials` بـ `packages/shared`). Supabase يخزنه `9647XXXXXXXXX`.
- **كل حساب برقم صالح:** trigger على `auth.users` (`before insert`، و`before update of phone` عند تغيّر الرقم) يرفض حساباً بلا هاتف أو برقم ليس `9647XXXXXXXXX` (`PHONE_INVALID`). لا حسابات بالبريد. لذلك `profiles.phone` موجود دائماً و`PHONE_REQUIRED` لا يمنع زبوناً حقيقياً.
- **رقم واحد = حساب واحد:** `auth.users.phone` فريد (GoTrue)، وفهرس فريد `profiles_phone_key` وقيد صيغة `profiles_phone_format`.
- **الـ PIN:** 6 أرقام بالضبط، يُرفض السهل (تكرار، تسلسل، أنماط شائعة، أرقام من الهاتف): `validatePin` بـ `packages/shared` عند التسجيل (بالتطبيق **وبالخادم** في دالة `signup`) وتغيير الرمز وإعادة ضبطه. GoTrue لا يرى الرمز (bcrypt)؛ حده الأدنى `minimum_password_length = 6` (يكفي لتغيير الرمز بـ `updateUser`). Leaked password protection **معطّل** (يرفض كل الرموز تقريباً).
- عند التسجيل ينشئ trigger صفاً في `profiles` بدور `customer`. السائقون والموظفون يسجلون بنفس الدالة `signup` (تطبيق السائق، أو تطبيق الزبون للموظف)، ثم الأدمن يغيّر دورهم من اللوحة (`set_user_role`).
- أول أدمن: يُعيَّن يدوياً بـ SQL من لوحة Supabase (RUNBOOK §7).
- **نسيان الـ PIN:** الزبون يراسل المتجر على واتساب من نفس الرقم؛ الأدمن يعيد الضبط عبر Edge Function `admin-reset-pin` (§8، تُبنى بـ T19).
- **التخمين:** حدود Supabase لكل IP (تسجيل/دخول: 30 كل 5 دقائق افتراضياً). لا قفل لكل حساب على خطتنا (Password Verification Hook لـ Teams/Enterprise فقط). الخطر وخطة التخفيف بـ ADR 0001 (CAPTCHA بـ T23، الترقية لاحقاً).
- إعدادات اللوحة المطلوبة لكل مشروع: RUNBOOK §6.

## 8) Edge Functions
| الدالة | المُشغِّل | العمل |
|---|---|---|
| `push-dispatch` | trigger (`after insert for each statement`) على `notification_outbox` يطلب الدالة بـ `pg_net`، + `pg_cron` كل دقيقة إن بقي شيء غير مرسل. المصادقة بترويسة `x-dispatch-secret` (سر بـ Vault، `verify_jwt = false`) | تحجز حتى 200 صف، تجمع الرموز حسب الجمهور (`user` / كل السائقين النشطين / الأدمن والموظفون النشطون)، ترسل كل رمز عبر مزوّده: Expo Push API بدفعات ≤100 (`channelId: orders`، أولوية عالية)؛ `fcm` يُتخطى بملاحظة بـ `last_error`. تحدّث `sent_at` أو `attempts` و`last_error` (حد أقصى 5 محاولات)، وتحذف الرموز التي يرجع لها `DeviceNotRegistered` |

| `admin-reset-pin` (T19) | لوحة الأدمن بـ JWT الأدمن (`POST {user_id, new_pin}`، `verify_jwt = false` منذ T23 F؛ التحقق بالدالة: `auth.getUser` + `profiles.role = 'admin'` ونشط) | إعادة ضبط PIN مستخدم نسيه (بعد رسالة واتساب من نفس الرقم): `validatePin` برقم الهدف، حد 20 محاولة/ساعة لكل أدمن (`admin_rate_hit`)، `updateUserById` ثم `record_pin_reset` (التدقيق + `must_change_pin` + حذف رموز الإشعارات) ثم `revoke_user_sessions`، وكل من الأخيرتين بمحاولتين إضافيتين عند الفشل (جلسة C M2). فشل التدقيق نهائياً ← الرمز المكتوب يُستبدل برمز عشوائي لا يعرفه أحد (لا رمز حي معروف بلا علامة) و`RESET_INCOMPLETE`؛ فشل إبطال الجلسات نهائياً ← `RESET_INCOMPLETE` (العلامة والتدقيق ثابتان). ← `200 {ok: true}`. الأخطاء: `NOT_AUTHENTICATED` ← 401، `NOT_ALLOWED` ← 403، `MFA_REQUIRED` ← 403 (أدمن بجلسة ليست aal2، T23 C1)، `PIN_CHANGE_REQUIRED` ← 403 (المستدعي أدمن برمز مؤقت)، `INVALID_REQUEST` ← 400/405، `USER_NOT_FOUND` ← 404، `ADMIN_ACCOUNT` ← 403 (هدف أدمن أو المستدعي نفسه)، `PIN_INVALID` ← 400 (`detail` = سبب الرفض من `validatePin`: الطول، رمز سهل، أو من رقم الهدف)، `TOO_MANY_RESETS` ← 429، `RESET_INCOMPLETE` ← 500 (الرمز تغيّر لكن التدقيق أو إبطال الجلسات لم يكتمل: **لا يُرسل الرمز**، أعد الضبط)، `INTERNAL` ← 500. التفاصيل: SPEC-admin §2.6 |
| `driver-register` (T28، منشورة على mukhdar-dev 2026-11-20؛ SPEC-driver §4.2) | تطبيق السائق قبل أي حساب (`POST {full_name, phone, device_secret, push_token?}`، `verify_jwt = false`؛ بلا Origin = التطبيق الأصلي، أو أصل من سر ALLOWED_ORIGINS للويب، وأي أصل آخر ← 403 `NOT_ALLOWED` قبل أي عمل) | `driver_request_rate_hit(ip, null)` **أولاً** (كل محاولة تُحسب حتى الجسم الخاطئ، على الـ IP وحده؛ 10/ساعة)، ثم `driver_request_rate_hit(null, phone)` **بعد اجتياز فحص الجسم والاسم والرقم والسر** (3/يوم لكل رقم؛ R1 M3: الطلب الفاسد لا يستهلك حصة رقم أحد). **الـ IP = `cf-connecting-ip` فقط** (تضعها Cloudflare أمام دوال Supabase وتستبدل/ترفض قيمة العميل؛ `x-forwarded-for` و`x-real-ip` لا تُقرأ أبداً لأن العميل يتحكم بها؛ بلا الترويسة ← مفتاح مشترك `unknown`) ← `normalizeIraqiPhone` ← الاسم 2..80 ← السر base64url = 32 بايت ← `push_token` بصيغة Expo وإلا يُهمل (null) ← SHA-256 ← `submit_driver_request` ← `201 {request_id}`. **لا تنشئ حساب Auth أبداً.** الأخطاء (`{"error": CODE}` عامة فقط، بلا نص قاعدة البيانات): `INVALID_REQUEST` ← 400/405، `PHONE_INVALID` ← 400، `NAME_INVALID` ← 400، `NOT_ALLOWED` ← 403، `RATE_LIMITED` ← 429، `PHONE_TAKEN` ← 409، `REQUEST_EXISTS` ← 409، `TOO_MANY_PENDING` ← 429، `REGISTER_FAILED` ← 500 (فشل الحد أو قاعدة البيانات: تفشل مغلقة). لا يُسجَّل الجسم ولا السر ولا الـ hash ولا الاسم ولا الرقم كاملاً (`9647******67`) |
| `driver-complete-registration` (T28، منشورة على mukhdar-dev 2026-11-20؛ SPEC-driver §4.4) | الجهاز الموافَق عليه (`POST {request_id, device_secret, pin}`، `verify_jwt = false`؛ نفس قاعدة الأصل) | حد IP أولاً (`driver_request_rate_hit(ip, null)`، نفس مفتاح `cf-connecting-ip` ونفس عدّاد التسجيل) ← الجسم ← SHA-256 للسر ← `begin_driver_completion` ← `validatePin` برقم الطلب ← `auth.admin.createUser` ← `finish_driver_registration` (فشلها ← حذف الحساب المُنشأ؛ إن فشل الحذف أيضاً يُسجَّل `ORPHAN` بمعرّف الحساب لحذفه يدوياً؛ وإن كان السبب `REQUEST_EXPIRED`/`REQUEST_NOT_APPROVED`/`REQUEST_NOT_FOUND` يرجع 410/409/404 لا 500، T31) ← `201 {created: true}`. ضغطتان متزامنتان ← حساب واحد: الثانية `PHONE_TAKEN` (GoTrue يرجع للخاسر أحياناً "Database error creating new user" بدل `phone_exists`، فتفحص الدالة `profiles.phone`: موجود ← 409، وإلا 500). الأخطاء: `INVALID_REQUEST` ← 400/405، `NOT_ALLOWED` ← 403، `RATE_LIMITED` ← 429، `REQUEST_NOT_FOUND` ← 404 (سر خاطئ أيضاً)، `REQUEST_NOT_APPROVED` ← 409، `REQUEST_EXPIRED` ← 410، `PIN_INVALID` ← 400 (`detail`)، `PHONE_TAKEN` ← 409 (الطلب يبقى `approved`)، `INTERNAL` ← 500. لا يُسجَّل الرمز ولا السر ولا الـ hash ولا الرقم كاملاً |

**المفاتيح وفحص الـ JWT (T23 F H2، 2026-11-17):** الدوال (الخمس، ودالتا السائق منذ T28) تقرأ المفتاح الجديد أولاً (متغيرا البيئة SUPABASE_SECRET_KEYS وSUPABASE_PUBLISHABLE_KEYS، المفتاح `default`) والقديم (SUPABASE_SERVICE_ROLE_KEY وSUPABASE_ANON_KEY) احتياطاً (`_shared/keys.ts`)، وتسجّل نوع المفتاح بلا قيمته (`keys {"secret":"new"}`). كل الدوال `verify_jwt = false` (بوابة Supabase تفهم مفاتيح JWT القديمة فقط، حسب توثيق Supabase الحالي)، والدوال التي تأخذ JWT مستخدم تتحقق منه بنفسها بـ `auth.getUser` (يقبل رموز HS256 القديمة ورموز مفاتيح التوقيع ES256): بلا `Bearer` أو برمز غير صالح ← 401 `NOT_AUTHENTICATED` قبل أي عمل. `push-dispatch` بسر `x-dispatch-secret` فقط (لا مفتاح بنداء `pg_net`). فإطفاء المفاتيح القديمة لا يكسر الدوال (RUNBOOK §17.5).

**خمول الجلسة (T23 M7):** الدالتان الإداريتان تستدعيان `touch_panel_session` بـ JWT المستدعي قبل أي عمل: جلسة خاملة أكثر من 12 ساعة ← 401 `SESSION_EXPIRED`، وتعذّر الفحص نفسه ← 500 `INTERNAL` (تفشل مغلقة).  

**CORS للدوال التي يستدعيها المتصفح (T23 H1؛ ومعاينة الويب: signup وdelete-account أيضاً):** Supabase المستضاف لا يضيف CORS للدوال، فالدالة نفسها (`_shared/cors.ts`) ترد على `OPTIONS`: أصل موجود بسر الدالة ALLOWED_ORIGINS (مفصول بفواصل؛ فارغ = لا شيء، و`*` يُتجاهل) ← 204 مع `Access-Control-Allow-Origin` = الأصل نفسه، `Allow-Methods: POST, OPTIONS`، `Allow-Headers: authorization, apikey, content-type, x-client-info, x-region, x-supabase-api-version`، `Vary: Origin`؛ أصل آخر ← 403 بلا ترويسات. الرد الحقيقي يحمل `Access-Control-Allow-Origin` للأصل المسموح فقط. طلب بلا `Origin` يمر بلا CORS (الحماية JWT الأدمن). `signup` و`delete-account` يستعملان الآلية نفسها (`createSignupServer`/`createDeleteAccountServer`) لتعمل PWA الزبون على الويب؛ التطبيقات الأصلية لا ترسل `Origin` فلا تتأثر. الاختبار `_shared/cors_test.ts` يستدعي ما تخدمه `index.ts` بلا Kong (Kong المحلي كان يضيف CORS فأخفى الخلل).

## 9) كيف نضمن الأداء
| الإجراء | التفصيل |
|---|---|
| منطق الطلب بقاعدة البيانات | رحلة شبكة واحدة لكل طلب، وقفل صفوف المخزون فقط (لا قفل للجدول كاملاً) |

| Realtime محدود | الزبون يشترك بـ `orders` بفلتر `id=eq.<order_id>` لطلبه الحالي فقط، ويلغي الاشتراك عند الوصول لحالة نهائية. السائق يشترك بطلباته المعيَّنة. الأدمن يشترك بالطلبات الجديدة فقط |

| الصور | bucket `product-images` بحد 512KB، والتطبيق يصغّر لعرض 800px قبل الرفع |
| Connection pooling | Edge Functions ولوحة الأدمن (server-side) تستخدم رابط Supavisor |
| اختبار حمل k6 | انظر أدناه |

### اختبار الحمل (k6)
- **السيناريو 1، ذروة الطلبات:** 300 مستخدم افتراضي، كل واحد يسجّل الدخول بحساب تجريبي ويستدعي `place_order` بسلة عشوائية من 1 إلى 8 بنود، لمدة 5 دقائق.
- **السيناريو 2، التصفح:** 500 مستخدم افتراضي يقرأون الأقسام والمنتجات بصفحات.
- **السيناريو 3، التنافس:** 200 طلب متزامن على منتج رصيده 50. **المطلوب:** 50 طلباً ناجحاً بالضبط، والرصيد 0، والباقي `INSUFFICIENT_STOCK`، وصفر deadlocks.
- **العتبات:** p95 لـ `place_order` < 500ms، p95 لقراءة الكتالوج < 300ms، نسبة الأخطاء غير المتوقعة < 0.5%.
- يُشغَّل على مشروع staging بنفس حجم Compute الإنتاجي، **لا على الإنتاج**.
- ملاحظة تاريخية (مرحلة المسودة، Postgres 16 محلي، قبل Supabase): 40 طلباً متزامناً على رصيد 10 أعطت 10 طلبات ناجحة بالضبط بلا deadlocks. التحقق الحالي المستمر بـ CI عبر سكربت التزامن (انظر RUNBOOK §8)، والقياس الفعلي بـ T22.

## 10) الاختبارات (pgTAP)

### 12.1 المخزون والكلفة (T18)
- `inventory_movements.unit_cost_iqd bigint` (≥ 0، مضاعفات 250 للمشتريات). يُملأ لكل حركة: `purchase` من السعر المُدخل؛ `waste` و`adjust` و`sale` و`cancel_return` من `product_costs` لحظة الحركة (0 إن لم يوجد سعر شراء، مع بقاء تنبيه "منتج بلا سعر شراء"). **Backfill على dev:** الحركات القديمة من سعر الشراء الحالي.
- `adjust_stock(p_product_id, p_qty, p_type, p_note?, p_unit_cost_iqd?)`: `purchase` يتطلب `p_unit_cost_iqd` (مضاعف 250) ويحدّث `product_costs` لآخر سعر؛ `adjust` يتطلب ملاحظة؛ `waste` و`adjust` السالبة تزيد `daily_stats` بـ `qty × unit_cost` (اليوم بتوقيت بغداد). الأخطاء الحالية (`INVALID_MOVEMENT` لسعر ناقص أو ملاحظة ناقصة).
- `adjust_stock_bulk(p_items jsonb, p_type, p_note?)` (أدمن): `[{product_id, qty, unit_cost_iqd?}]` بمعاملة واحدة، بأقفال `stock` بترتيب `product_id`؛ أي بند خاطئ يُفشل الكل (`detail` = المنتج). لهدر اليوم (ويقبل المشتريات بالجملة).
- `daily_stats`: أعمدة `waste_cost_iqd` و`adjust_loss_iqd` (≥ 0)، و`net_profit_iqd` = `gross_profit_iqd - waste_cost_iqd - adjust_loss_iqd` (عمود محسوب). `_bump_daily_stats` يقبلها.
- `recompute_daily_stats(p_from date, p_to date)` (أدمن/service_role): يعيد بناء الأيام من `orders` و`order_item_costs` و`inventory_movements` (للتصحيح وللـ backfill)؛ اختبار pgTAP يقارن التحديث التراكمي بإعادة البناء.
- **حد النقص:** `stock.low_stock_threshold int not null default 5` (0..10000). عند أي تغيير رصيد (البيع بـ `place_order`، الإلغاء، `adjust_stock*`) ينزل فيه الرصيد من ≥ الحد إلى < الحد ← `_notify('admins_only', …)` مرة واحدة (`type: low_stock`، `product_id`، النص: الاسم والرصيد بالكيلو لنص الكيلو أو بالوحدة). العودة فوق الحد ثم النزول = إشعار جديد. لا إشعار للموظفين: **حُسم بالبناء** بجمهور جديد `admins_only` (الأدمن وحده) بقيد `notification_outbox` و`claim_push_notifications`؛ trigger على `stock` (لمنتج نشط فقط).
- اختبار ثابت (invariant): لكل منتج `stock.qty = Σ inventory_movements.qty` (الـ seed يُنشئ حركة رصيد افتتاحي بدل كتابة `stock` مباشرة).

### 12.8 إصلاح: triggers التنظيف بدور المالك (بلاغ iOS Safari، 2026-11-18، migration `20261203000001`)
- **العَرَض:** بعد التسجيل، حفظ الاسم (وإضافة/تعديل العنوان) يفشل للزبون بـ "حدث خطأ غير متوقع". السبب: `private.tg_clean_profile_name` و`private.tg_clean_address_text` (§12.6) كانتا SECURITY INVOKER وتستدعيان `private.clean_user_text` المسحوبة من كل الأدوار ← `42501`. لم يظهر بالاختبارات لأنها كتبت الاسم والعنوان بدور postgres.
- **الإصلاح:** الدالتان SECURITY DEFINER بـ `search_path = ''`، وEXECUTE مسحوب من كل الأدوار (لا يُفحص EXECUTE لدالة trigger عند تشغيلها).
- **تدقيق القاعدة كلها لنفس الصنف** (mukhdar-dev): دوال triggers الأخرى بـ INVOKER (`set_updated_at`، `tg_profiles_pin_reset_at`، `tg_require_valid_phone` على `auth.users`) لا تستدعي إلا `now()`/regex؛ سياسات RLS تعتمد على `private.is_admin`/`is_staff_or_admin`/`current_user_role` (definer) و`baghdad_today` و`auth.uid`، وكلها قابلة للتنفيذ من `anon` و`authenticated` مع USAGE على `private`؛ القيم الافتراضية `gen_random_uuid()`/`now()`؛ دوال INVOKER القابلة للاستدعاء (`set_default_address`، `panel_session_alive`، `round_iqd`، `baghdad_today`، أغلفة الأدوار، `finish_push_notifications` لـ service_role) لا تصل لشيء محجوب. **لا مشكلة أخرى**؛ `32_real_role_writes.sql` يحرس الصنف آلياً.
- **رسالة الصلاحية:** خطأ `42501` بلا رمز معروف (صلاحية ناقصة أو سياسة RLS رفضت الصف) يُعرض بـ `PERMISSION_ERROR_MESSAGE` (`packages/shared/src/errors.ts`): "ما قدرنا نحفظ هذا التغيير لأن حسابك ما عنده صلاحية له…" بدل الرسالة العامة. الرموز المعروفة التي تُرفع بـ 42501 (`NOT_ALLOWED`، `PIN_CHANGE_REQUIRED`…) تبقى برسائلها. ليست رمزاً بـ §5 (لا ترفعها دالة).

### 12.9 الطابق بالعنوان (قرار المالك 2026-11-18، migration `20261204000001`)
- `addresses.floor smallint` (قيد `addresses_floor_range`: 0..20، 0 = الأرضي). **null مسموح للعناوين القديمة فقط.** trigger `addresses_clean_text` (definer) يرفض `FLOOR_REQUIRED` لعنوان **جديد من دور `authenticated`** بلا طابق، أو مسح طابق مسجَّل؛ عنوان قديم بلا طابق يبقى يُعدَّل ويُطلب إليه. سكربتات التطوير بدور المالك غير مقيّدة (`seed:demo` يضع طابقاً 0..9 على أي حال). `authenticated` له `insert/update (floor)`.
- **اللقطة:** trigger `orders_snapshot_floor` (before insert على `orders`، definer) يضيف `"floor"` (رقم) لـ `address_snapshot` من العنوان وقت الطلب، فلا تُعاد كتابة `place_order`. عنوان بلا طابق ← لا مفتاح. تجهيل حساب محذوف يبني اللقطة من `sector` و`subsection` فقط، فيُحذف الطابق.
- **لا تغيير:** شجرة قطاع ← وحدة ← عمارة، `available_orders` (لا شقة ولا طابق قبل القبول)، نص الإشعارات (غُيّر لاحقاً بنفس اليوم إلى "بلوك A3 - بناية 12"، `20261205000001`).
- العرض: `formatAddress` بـ `packages/shared` يضيف "طابق N" ("الطابق G" لـ 0، ولم تعد "الأرضي") بين العمارة والشقة ("الطابق G" لـ 0 منذ 2026-11-19): تطبيق الزبون، تفاصيل الطلب والإيصال باللوحة.


### 12.10 نطاقات بسماية بالعنوان (قرار المالك 2026-11-19، migration `20261207000001`)
- **الشجرة (بيانات لا migration):** البلوكات الفعّالة A1..A9 وB1 وB2 وB3 وB8، وبنايات كل بلوك 1..N (A1 12، A2 14، A3 14، A4 12، A5 12، A6 12، A7 13، A8 15، A9 15، B1 12، B2 18، B3 18، B8 12). يطبّقها `scripts/address-tree/run.mjs` من `data.json` (قابل للإعادة، معاينة بلا `--apply`؛ يُخفي الباقي ولا يحذف شيئاً؛ مرفوض على الإنتاج إلا بالمسار الصريح الثلاثي كسكربت الصور). يطبع العناوين المحفوظة غير الصالحة.
- **trigger `addresses_clean_text`** (نفس الدالة definer + قواعد جديدة، **لكل الأدوار**): طابق خارج 0..9 ← `FLOOR_INVALID`؛ شقة لا تطابق `^([1-9]|1[0-2])$` (يشمل الفراغ والأرقام العربية والنص الحر) ← `APARTMENT_INVALID`؛ عمارة غير فعّالة أو ببلوك/قطاع غير فعّال ← `BUILDING_INACTIVE`. **عند الإدراج، وعند تعديل الحقل نفسه فقط** (`is distinct from` القيمة القديمة): العنوان القديم غير الصالح يبقى يُعدَّل بملاحظته أو يُجعل افتراضياً بلا اعتراض، لكن تغيير شقته لقيمة غير صالحة مرفوض. قيد `addresses_floor_range` (0..20) باقٍ لأنه يشمل صفوفاً قديمة.
- **افتراض:** `place_order` لا يرفض عنواناً قديماً غير صالح (التطبيق لا يرسل منه، SPEC-customer §2.5)؛ لم نعدّل دالة الطلب الكبيرة، والمخاطرة تجارية فقط (لقطة بشقة خارج النطاق) لا أمنية.
- العناوين غير الصالحة بـ mukhdar-dev بعد التطبيق: 30 من 31 (طابق ناقص أو شقة خارج 1..12 أو عمارة/بلوك مخفي)؛ كلها بيانات تجريبية بطلباتها، لم تُمس.
