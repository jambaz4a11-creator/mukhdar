# ADR 0001: الدخول برقم الهاتف + PIN من 6 أرقام، بدون SMS

- **الحالة:** مقبول (2026-11-14). يحل محل خطة "OTP عبر SMS" (T04 القديمة).
- **القرار من:** صاحب المشروع (لا SMS/OTP: كلفة الرسائل بالعراق عالية). التفاصيل التقنية بهذا الملف.
- **التنفيذ:** migration `20261116000001_phone_pin_auth.sql`، `packages/shared/src/pin.ts`، `supabase/config.toml`، اختبار `supabase/tests/13_phone_pin_auth.sql`. الشاشات بـ T10 (الزبون)، T16 (الأدمن)، وتطبيق السائق الخارجي (DRIVER-API §1).

## السياق
- كل المستخدمين (زبائن، موظفون، سائقون، أدمن) يسجّلون ويدخلون برقم الهاتف + رمز PIN من 6 أرقام.
- **لا تُرسل أي رسالة أبداً** (لا SMS ولا بريد ولا واتساب): كلفة رسائل صفر.
- المتطلبات: حساب واحد لكل رقم؛ `profiles.phone` موجود دائماً بالصيغة الموحّدة (حتى لا يمنع `PHONE_REQUIRED` زبوناً حقيقياً)؛ PIN 6 أرقام بالضبط؛ رفض الرموز السهلة.

## ما تحققنا منه (توثيق Supabase، نوفمبر 2026)
| الموضوع | النتيجة |
|---|---|
| تسجيل بالهاتف + كلمة سر | مدعوم (`signUp({ phone, password })`، `signInWithPassword({ phone, password })`). التوثيق يقول إن **تأكيد** الهاتف عند التسجيل يحتاج مزوّد SMS؛ بإيقاف "Enable phone confirmations" لا يُرسل رمز ويرجع التسجيل بجلسة مباشرة (`SMS_AUTOCONFIRM`). |
| Send SMS Hook | متاح على Free وPro، ويقبل دالة Postgres (`pg-functions://postgres/<schema>/<fn>`). حين يُفعَّل يحل محل مزوّد SMS. إن أرجع خطأ، تفشل العملية التي طلبت الإرسال. |
| Password Verification Hook (عدّاد محاولات وقفل لكل حساب) | **Teams وEnterprise فقط**. غير متاح لنا على Free/Pro. |
| حدود المعدل | لكل IP، قابلة للتعديل من Authentication ← Rate Limits. الافتراضي لتسجيل الدخول والتسجيل: **30 طلباً كل 5 دقائق لكل IP** (`sign_in_sign_ups`)، وتجديد التوكن 150 كل 5 دقائق. (صفحة Production Checklist القديمة تذكر أرقاماً بالساعة؛ صفحة Rate limits أحدث.) |
| البريد الافتراضي (بديل البريد المصطنع) | SMTP الافتراضي يرسل فقط لأعضاء المنظمة (`email_address_not_authorized`)، ونطاقات example/test مرفوضة (`email_address_invalid`). استعادة كلمة السر ترسل بريداً حتى مع إيقاف التأكيد. |
| Leaked password protection (HaveIBeenPwned) | كل الأرقام من 6 خانات تقريباً موجودة بقوائم التسريب، فتفعيله **يرفض كل الـ PINs تقريباً**. يبقى **معطّلاً**. |

## الخيارات
**أ) هاتف + كلمة سر (الـ PIN)، تأكيد الهاتف معطّل، وSend SMS Hook يرفض كل إرسال.** ← **المختار**
- الرقم بعمود `auth.users.phone` الأصلي، فريد من GoTrue نفسه. الـ trigger الموجود (`tg_handle_new_user` و`tg_sync_user_phone`) ينسخه لـ `profiles.phone` بلا تغيير.
- الـ hook يرفض: `signInWithOtp` (لا ينشئ حساباً لرقم غيره، لأن فشل الإرسال يلغي المعاملة)، إعادة الإرسال، تغيير الرقم من التطبيق (يحتاج OTP، فيُرفض: تغيير الرقم بالأدمن فقط)، `reauthenticate`. **الكلفة صفر حتى لو ضُبط مزوّد SMS بالخطأ**، لأن الـ hook يسبق المزوّد.
- مزوّد Email يبقى **معطّلاً** بالإنتاج (لا بريد يُرسل ولا حساب بالبريد).
- محلياً وفي CI هذا هو الإعداد من الأصل (`[auth.sms] enable_confirmations = false`، email معطّل).

**ب) بريد مصطنع من الرقم (`9647…@phone.<domain>`) + كلمة سر، تأكيد البريد معطّل.** ← مرفوض
- النطاق يجب أن يمر بتحقق Supabase (example/test مرفوضة)، و**لا يجوز أن يصل له بريد**: إن ضُبط SMTP مخصص يوماً، "نسيت كلمة السر" أو تغيير البريد يرسل رابطاً لنطاق قد يملكه غيرنا ← **استيلاء على الحساب**. يحتاج نطاقاً نملكه أو Send Email Hook يرفض.
- `profiles.phone` يُستخرج من نص البريد، وتغيير البريد مع التأكيد التلقائي يغيّر هوية الحساب: منطق إضافي وحالات حافة.
- يُبقي مزوّد Email مفعّلاً بالإنتاج (عكس قرارنا السابق).

**ج) دخول عبر Edge Function خاصة (PIN مخزن عندنا مع عدّاد وقفل).** ← مؤجل كخيار ترقية
- واجهة GoTrue لكلمة السر تبقى مفتوحة بمفتاح anon، فلا قيمة للعدّاد إلا إذا صارت كلمة السر الحقيقية سراً مشتقاً (`HMAC(pepper, phone‖PIN)`) لا يعرفه إلا الخادم.
- الدالة تستدعي GoTrue من IP واحد، وحد 30 طلباً كل 5 دقائق لكل IP يصير حداً **لكل المستخدمين معاً**. يحتاج تحققاً قبل الاعتماد عليه، وكوداً وصيانة (تدوير الـ pepper يبطل كل الرموز).

## القرار
الخيار (أ)، مع:
1. **Send SMS Hook:** `private.hook_send_sms_reject(jsonb)` يرجع دائماً `{"error": {"http_code": 403, ...}}`. تنفيذه لـ `supabase_auth_admin` فقط.
2. **كل حساب برقم صالح:** trigger `before insert` و`before update of phone` على `auth.users` (`private.tg_require_valid_phone`) يرفض حساباً بلا هاتف أو برقم ليس `9647XXXXXXXXX` (`PHONE_INVALID`). فلا يوجد حساب بلا `profiles.phone`، ولا حساب بالبريد فقط من اللوحة.
3. **رقم واحد = حساب واحد:** فريد بـ `auth.users` (GoTrue)، وفهرس فريد `profiles_phone_key` + قيد صيغة `profiles_phone_format` بجدولنا.
4. **الـ PIN:** `validatePin` و`normalizePin` و`phonePinCredentials` بـ `packages/shared` (6 أرقام لاتينية بعد تحويل الأرقام العربية؛ رفض التكرار والتسلسل والأنماط الشائعة وأرقام الهاتف نفسه). الخادم لا يرى الـ PIN (bcrypt)، فلا يستطيع فحص السهولة؛ الحد الأدنى بالخادم `minimum_password_length = 6` بلا متطلبات أحرف.
5. **نسيان الـ PIN:** الزبون يراسل المتجر على واتساب **من نفس الرقم**؛ الأدمن يعيد ضبط الرمز من اللوحة عبر Edge Function `admin-reset-pin` (أدمن فقط، SPEC-admin §2.6، تُبنى بـ T19). رسالة الواتساب من نفس الرقم هي التحقق من الملكية.

## العواقب والمخاطر
### 1) التخمين (brute force)
- المساحة: 10⁶ رمز ناقص المرفوض (~50 رمزاً). بحد 30 محاولة كل 5 دقائق لكل IP: **8,640 محاولة يومياً من IP واحد** ← متوسط ~58 يوماً لكسر رقم واحد. 100 IP (botnet) ← ~14 ساعة. لا يوجد قفل لكل حساب على خطتنا.
- **انتبه لـ CGNAT:** شركات الاتصالات بالعراق تشارك IP واحداً بين مستخدمين كثيرين. تخفيض حد الـ IP كثيراً يقفل زبائن حقيقيين؛ نبقيه 30/5 دقائق ونراقب أخطاء 429.
- الدخول الخاطئ يرجع `invalid_credentials` نفسه للرقم غير المسجل وللرمز الخاطئ (لا كشف بالدخول). التسجيل يكشف أن الرقم مسجل (`user_already_exists`): قيمة منخفضة، مقبول.
- **ما أُضيف الآن (رخيص وآمن):** رفض الرموز السهلة بالتطبيقات؛ رفض كل SMS (لا كلفة ولا إساءة رسائل)؛ لا Test OTPs (كانت رموزاً ثابتة يدخل بها أي أحد).
- **لم يُضف عدّاد وقفل:** على Free/Pro لا يرى Postgres المحاولات الفاشلة (لا hook تحقق كلمة السر)، وبديل Edge Function (خيار ج) غير آمن قبل التحقق من حد الـ IP. **الخطر مسجل** والخطة:
  1. **T23 (مراجعة الأمان):** فحص Auth logs لمحاولات فاشلة متكررة؛ قرار بشأن **CAPTCHA** لـ Auth (Supabase يدعم hCaptcha وCloudflare Turnstile مجاناً على signup/signin؛ يحتاج دعماً بشاشة الدخول بالتطبيقات).
  2. **حسابات الأدمن والموظفين** قيمتها أعلى (ترى هواتف وعناوين الزبائن): قليلة العدد، والأدمن يراجع قائمة الموظفين، ويعطّل أي حساب فوراً (`set_user_role` ← `is_active = false`، و`delete-account`/إعادة الضبط تبطل الجلسات). **افتراض:** نفس طريقة الدخول للجميع (قرار المالك)؛ إن ظهرت محاولات على حسابات الإدارة، يُرفع حد طول الرمز للأدوار الإدارية أو يُفعَّل CAPTCHA للوحة أولاً.
  3. **مسار الترقية:** خطة Teams ← Password Verification Hook (مثلاً 5 أخطاء ← قفل 15 دقيقة للحساب)، أو خيار (ج) بعد قياس حد الـ IP على مشروع التطوير.

### 2) ملكية الرقم غير مُتحقق منها
- بلا رسائل لا نثبت أن المسجّل يملك الرقم: أي شخص يستطيع تسجيل رقم غير مسجل بعد (حجز رقم غيره)، أو إرسال طلب باسم رقم غيره (السائق يتصل بصاحب الرقم الحقيقي).
- **التخفيف:** صاحب الرقم الحقيقي يراسل المتجر على واتساب من رقمه ← الأدمن يعيد ضبط الـ PIN للحساب (فيأخذه صاحبه) أو يعطّله. حد الطلبات المفتوحة (3) والدفع عند التسليم يحدّان الضرر. التحقق عبر واتساب لاحقاً، اختياري (T04).

### 3) أخرى
- تغيير الرقم من التطبيق غير ممكن (الـ hook يرفض OTP التغيير). تغيير الرقم = الأدمن (لاحقاً) أو حساب جديد.
- تغيير الـ PIN من "حسابي" (`updateUser({ password })`، بعد إعادة إدخال الرمز الحالي) بـ T15؛ الخادم لا يفرض قواعد السهولة على كلمة سر يرسلها عميل معدّل (خطر على صاحبه فقط).
- Leaked password protection يبقى معطّلاً (يرفض كل الرموز تقريباً).
- T04 صارت "تحقق عبر واتساب (لاحقاً، اختياري)" ولا تمنع شيئاً؛ رقم ADR الخاص بها يصبح 0004.

## إعدادات اللوحة المطلوبة (لكل مشروع: التطوير والإنتاج)
تُضبط يدوياً من صاحب المشروع (RUNBOOK §6). بالترتيب:
1. Authentication ← **Hooks** ← Send SMS hook: **Enabled**، النوع **Postgres**، الدالة `private.hook_send_sms_reject`.
2. Authentication ← Sign In / Providers ← **Phone**: **Enabled**؛ **Enable phone confirmations: OFF**. إن طلبت اللوحة مزوّد SMS رغم تفعيل الـ hook: اختر Twilio بقيم وهمية؛ لا تُستخدم أبداً لأن الـ hook يسبق المزوّد ويرفض.
3. Authentication ← Sign In / Providers ← **Allow new users to sign up: ON**.
4. Authentication ← Policies/Passwords: **Minimum password length = 6**، **Password requirements = No required characters**، **Leaked password protection: OFF**.
5. Authentication ← Rate Limits ← sign-ups and sign-ins: **30 / 5 دقائق** (الافتراضي؛ لا تخفّضه بسبب CGNAT).
6. **الإنتاج فقط:** Email provider **Disabled**. (بالتطوير يبقى مفعّلاً لاختبار `it:delete-account`.)

## التحقق بعد ضبط اللوحة
- `signUp({ phone: '+9647…', password: '<PIN>' })` يرجع جلسة، و`profiles.phone` = `9647…`.
- `signInWithPassword` بالرمز الصحيح ينجح، وبالخاطئ `invalid_credentials`.
- `signInWithOtp({ phone })` يفشل ولا يُنشأ حساب.
- مستخدمو العرض (`seed:demo`) يدخلون بـ `DEMO_PIN` (RUNBOOK §6).
