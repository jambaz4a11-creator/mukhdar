# 17: صفحة الطلبات ✅

**الهدف:** SPEC-admin §2.1.

## الخطوات
- تبويبات الحالات مع عدادات (استعلام `count` بالحالة، `head: true`).
- جدول بصفحات 50 (keyset)، فلاتر، بحث برقم الطلب أو الهاتف.
- Realtime على `INSERT` مع صوت، و`UPDATE` للمعروض.
- جدول الطلبات مكوّن واحد قابل لإعادة الاستخدام (فلتر جاهز "اليوم" للرئيسية بـ T25).
- لوحة التفاصيل: الزبون (الاسم، الهاتف)، العنوان الكامل (`formatAddress`) وملاحظته، ملاحظة الطلب، بنود، سجل الحالات، التقييم، أزرار حسب الدور (`set_order_status` ومنها "جاهز" ← `ready`، `assign_driver` من `preparing`/`ready`)، تكلفة وربح للأدمن.
- صفحة طباعة 80mm.

## القبول
- طلب من تطبيق الزبون يظهر باللوحة خلال ثانيتين بصوت تنبيه.
- الموظف لا يرى أعمدة التكلفة (لا تُجلب أصلاً).

## الاختبارات
- Playwright: بدء تحضير، تعيين سائق، إلغاء بسبب، فلترة، بحث، طباعة تفتح.
- وحدة: أزرار الإجراءات الصحيحة لكل (حالة × دور)؛ عرض العنوان الكامل والهاتف بلوحة التفاصيل.

## ملاحظات التنفيذ (2026-11-16)
- `apps/admin/src/features/orders`: `actions.ts` (أزرار حسب الحالة × الدور)، `filters.ts` (التبويبات، يوم بغداد، البحث، keyset)، `api.ts` (القراءة والـ RPC)، `OrdersTable.tsx` (المكوّن القابل لإعادة الاستخدام بـ T25)، `OrdersScreen.tsx`، `OrderDetailPanel.tsx`. الإيصال: `/print/orders/[id]` (80mm، بلا كلفة).
- Realtime: اشتراك واحد بـ `PanelProviders` لكل صفحات اللوحة: INSERT ← صوت (Web Audio، يُفتح بأول نقرة) + إبطال استعلامات الطلبات (الطلب يظهر أعلى "جديد" مع تمييز)، UPDATE ← إبطالها؛ شارة القائمة من نفس الاشتراك.
- الكلفة والربح: `order_item_costs` تُطلب للأدمن فقط (`fetchOrderCosts` يرجع null للموظف بلا استعلام؛ اختبار وحدة + Playwright يراقب الشبكة).
- الاختبارات: وحدة 100 (منها مصفوفة الحالة × الدور)، Playwright 26. تدفقات الكتابة (طلب حي، تحضير، تعيين، جاهز، إلغاء) بـ CI فقط (`E2E_ALLOW_WRITES=1` ضد Supabase محلي مع Realtime)؛ محلياً ضد mukhdar-dev اختبارات القراءة فقط.
