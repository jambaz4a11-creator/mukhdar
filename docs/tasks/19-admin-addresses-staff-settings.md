# 19: العناوين والموظفون والإعدادات

**الهدف:** SPEC-admin §2.4 و§2.6 (ومنها إعادة ضبط الـ PIN وإنشاء الحسابات) و§2.7، وSPEC-backend §12.2 (الإعدادات).
قاعدة الكيلو (SPEC-admin §2.9) لا تنطبق هنا: الأجرة والحد الأدنى مبالغ بالدينار كما هي، ولا كميات منتجات بهذه الصفحات. الشكل حسب شاشة "Settings" بالتصميم المعتمد.

## الخطوات
- شجرة العناوين (قطاع ← وحدة ← عمارة) مع إضافة عمارات بالجملة لوحدة (مدى أو قائمة، معاينة، تجاهل المكرر بـ `on conflict do nothing`).
- الموظفون: قائمة غير الزبائن، بحث بالهاتف (لأي حساب)، تغيير الدور والتفعيل (`set_user_role`).
- **إعادة ضبط رمز الدخول (نسيت الـ PIN)** حسب المواصفة بـ SPEC-admin §2.6 (ADR 0001):
  - Edge Function جديدة `admin-reset-pin` (أدمن فقط، لا لحسابات الأدمن، حد 20/ساعة لكل أدمن، `updateUserById` بكلمة السر الجديدة، إبطال الجلسات، سجل تدقيق، الرمز لا يرجع ولا يُسجَّل).
  - `revoke_user_sessions(p_user_id)` (service_role فقط) **موجودة** (migration `20261119000001`، مراجعة T09-T15، مطبقة على mukhdar-dev): الدالة تستدعيها بعد `updateUserById`. migration جديدة: جدول `pin_resets` (قراءة للأدمن فقط بـ RLS) وصلاحيات `service_role` المطلوبة (وتحديث فحص `01_schema.sql`).
  - رموز `PIN_INVALID` و`TOO_MANY_RESETS` بـ `packages/shared/errors.ts` وSPEC-backend §5.
  - الواجهة: زر بصف المستخدم، تحذير "رسالة الواتساب من نفس الرقم"، رمز يدوي أو عشوائي (يمر بـ `validatePin`)، يظهر مرة واحدة مع نسخ ورابط `wa.me`.
  - نشر الدالة على mukhdar-dev بموافقة صاحب المشروع.
- **إنشاء حساب موظف أو سائق** حسب SPEC-admin §2.6 (`admin-create-user`):
  - Edge Function (أدمن فقط، دور `staff` أو `driver` فقط، `validatePin` للرمز المؤقت، حد 20/ساعة، `auth.admin.createUser` ثم الدور، حذف الحساب إن فشل ما بعده).
  - migration: جدول `user_creations` (قراءة للأدمن فقط بـ RLS).
  - رموز الأخطاء إلى SPEC-backend §8 وerrors.ts.
  - الواجهة: "إضافة موظف أو سائق" بقائمة الموظفين، الرمز يظهر مرة واحدة مع نسخ و`wa.me`، والرقم المسجّل يقترح الترقية.
  - نشر الدالة على mukhdar-dev بموافقة صاحب المشروع.
- الإعدادات: أجرة التوصيل، الحد الأدنى، حد الطلبات المفتوحة، فتح/غلق المتجر ورسالته، مؤشر الإشعارات العالقة؛ الحفظ بـ `update_app_settings` (migration: الدالة، قيد `min_order_iqd % 250 = 0`، سحب update المباشر على `app_settings`).

## القبول
- إضافة عمارات 1..100 لوحدة بعملية واحدة (التسميات: "وحدة"، "عمارة").
- إغلاق المتجر يظهر الشريط بتطبيق الزبون ويمنع الطلب.
- حد أدنى 1100 مرفوض بالنموذج وبقاعدة البيانات؛ لا update مباشر على `app_settings`.
- إنشاء سائق برقم جديد: يدخل بالرمز المؤقت ويظهر بقائمة التعيين (`list_drivers`)؛ رقم مسجّل ← "الرقم مسجّل" بلا حساب ثانٍ.
- بعد إعادة ضبط PIN زبون: الرمز القديم يفشل، الجديد ينجح، والجلسات القديمة لا تتجدد.

## الاختبارات
- وحدة: تحليل المدى والقوائم ("1-100"، "1,2,5-9"، مدخلات خاطئة).
- Playwright: ترقية رقم لسائق؛ محاولة الأدمن تخفيض نفسه تظهر رسالة؛ إعادة ضبط PIN زبون تعرض الرمز مرة واحدة.
- `deno test` لـ `admin-reset-pin` (fetch مزيف): غير أدمن ← 403، هدف أدمن ← 403، رمز سهل ← 400، الحد ← 429، نجاح.
- `deno test` لـ `admin-create-user`: غير أدمن، دور `admin`/`customer` ممنوع، رمز سهل، رقم مكرر، الحد، نجاح يكتب الدور والسجل، فشل بعد الإنشاء يحذف الحساب.
- pgTAP: `update_app_settings` (أدمن فقط، قيد 250) وRLS `user_creations`.
- Playwright: إنشاء سائق يعرض الرمز مرة واحدة.
- pgTAP: RLS `pin_resets` (`revoke_user_sessions` مغطاة بـ `17_revoke_user_sessions.sql`).
- تكامل على dev (مثل `it:delete-account`): القديم يفشل والجديد ينجح بعد الضبط؛ وحساب مُنشأ بـ `admin-create-user` يدخل بدوره.
