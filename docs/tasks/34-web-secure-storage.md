# 34: التخزين المشفَّر للويب (W1) ⬜

**الهدف:** SPEC-webpush §6. بديل `localStorage`/SecureStore على الويب: IndexedDB + مفتاح WebCrypto غير قابل للتصدير، لجلسة Supabase وسر جهاز السائق وبيانات التسجيل، بوحدة واحدة مشتركة.
**يعتمد على:** - (مستقلة عن T33 وعن W2).
**النموذج المقترح:** **Opus** (أمان وتشفير).
**على dev:** لا migration ولا Edge Function ولا سر ولا Cloudflare. (يُنشر مع الزبون بالدمج التلقائي بـ `main` كأي تغيير بالزبون.)
**الحجم:** M.

## الخطوات
1. `packages/shared`: وحدة متصفح فقط (بلا استيراد expo) تنفّذ `{getItem, setItem, removeItem}` (نفس `ChunkedStorage` بلا تقسيم): مفتاح AES-GCM 256 بـ `extractable: false` يُحفظ ككائن `CryptoKey` بـ IndexedDB، IV عشوائي 12 بايت لكل كتابة، قيمة مخزَّنة = `{iv, ct}`.
2. حالات حدّية: فشل فك التشفير أو غياب المفتاح مع وجود بيانات ← يُعامَل "لا قيمة" ويمسح الإدخال (لا استثناء ولا حلقة)؛ IndexedDB غير متاح (وضع خاص) ← مخزن ذاكرة مع علامة `degraded` يقرؤها التطبيق لشريط تنبيه؛ `navigator.storage.persist()` عند البدء (أفضل جهد).
3. ربط الزبون: `apps/customer/src/lib/secureStorage.web.ts` يستعمل الوحدة. **ترحيل لمرة واحدة** لجلسة `localStorage` الحالية (قراءة ← تشفير ← حذف من `localStorage`).
4. تجهيز السائق: واجهة جاهزة لـ `secureStorage.web.ts` و`secureStore.web.ts` (تُربط فعلياً بـ W4).
5. SPEC-customer (فقرة التخزين على الويب) وSPEC-webpush §6 إن تغيّر قرار.

## القبول
- لا قيمة نصية صريحة بـ `localStorage` ولا IndexedDB للجلسة (فحص بالاختبار: القيمة المخزَّنة ≠ الأصلية، ولا تحوي أجزاءً منها).
- المفتاح لا يُصدَّر (`exportKey` يفشل)، ويبقى بعد إعادة التحميل.
- مفتاح مفقود/بيانات تالفة ← "لا جلسة" لا انهيار.
- جلسة الزبون الموجودة تُرحَّل مرة ولا تبقى نسخة بـ `localStorage`.
- Playwright للزبون (Chromium **وWebKit**) يمر: الدخول ثم إعادة التحميل يُبقي الجلسة.

## الاختبارات
- Jest (محاكاة IndexedDB وWebCrypto): تشفير/فك، IV مختلف لكل كتابة، تلف البيانات، غياب IDB، الترحيل، الحذف.
- Playwright الزبون الحالي على Chromium وWebKit (`apps/customer/e2e`).
- CI كامل أخضر؛ اختبارات كل حزمة محلياً على حدة.
