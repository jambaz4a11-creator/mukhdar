# 33: APK السائق والفحص على أجهزة حقيقية ⬜

**الهدف:** SPEC-driver §9 (معايير النجاح): APK داخلي لـ Android يعمل على dev بدورة كاملة. iOS Ad Hoc **ليس ضمن هذه المهمة** (لاحقاً، يحتاج حساب Apple Developer وUDID الأجهزة).
**يعتمد على:** 32، ومراجعة R2 منجزة وكل بنودها محلولة.
**النموذج المقترح:** Sonnet (بناء وفحص يدوي موجّه وتقرير).
**على dev:** لا migration ولا Edge Function جديدة. **بموافقة صاحب المشروع:** `eas build -p android --profile preview` (APK يشير لـ mukhdar-dev)، وتوزيعه على جهازين.
**الحجم:** S (كود قليل؛ أغلبها فحص وتقرير).

## الخطوات
1. التحقق قبل البناء: CI أخضر على `main`، `pnpm sb migration list --remote` بلا اختلاف، الدالتان منشورتان، متغيرات EAS لـ `preview` (URL ومفتاح dev، رقم المحل وواتساب، `GOOGLE_SERVICES_JSON`).
2. `eas build -p android --profile preview` ← رابط APK (لا يُرفع لـ git).
3. الفحص على جهازين Android حقيقيين + تطبيق الزبون + اللوحة، حسب SPEC-driver §9 البنود 3–6:
   - التسجيل ← المكالمة والموافقة ← التحويل (إشعار أو 30 ثانية) ← اختيار الرمز ← الدخول؛ الجهاز الثاني بنفس الرقم يفشل؛ طلب مرفوض لا يدخل.
   - طلب من الزبون ← تحضير و"جاهز" ← إشعار للسائقين ← قبول متزامن (واحد ينجح) ← "بالطريق" ← "تم التوصيل" ← تقييم الزبون ← سجل اليوم.
   - `الطابق G`، الاتصال والواتساب، ملاحظة الزبون.
   - نسيان الرمز ← `admin-reset-pin` ← دخول بالمؤقت ← تغيير إجباري.
   - تسجيل الخروج وحذف الحساب.
4. التقرير `docs/reviews/driver-apk-T33.md`: الأجهزة وإصدارات Android، كل بند ناجح/فاشل مع لقطة، والمشاكل المفتوحة.
5. `docs/PREVIEW.md`: قسم مختصر لصاحب المتجر (تثبيت APK، حسابات العرض للسائق).

## القبول
- كل بنود SPEC-driver §9 ناجحة على الجهازين، أو كل فشل له مهمة إصلاح مكتوبة (القاعدة 7: لا تجاوز).
- التقرير مدموج بـ `main`.

## الاختبارات
- كل اختبارات CI خضراء على الـ commit المبني منه.
- الفحص اليدوي الموثّق بالتقرير هو اختبار هذه المهمة.
