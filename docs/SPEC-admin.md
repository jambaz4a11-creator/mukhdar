# SPEC-admin: لوحة الأدمن (Next.js)

> `apps/admin`. Next.js (App Router) + Tailwind + `@supabase/ssr`. عربي RTL (`<html dir="rtl" lang="ar">`). تعمل على الحاسوب أولاً وتبقى صالحة على الموبايل.
> القراءة والكتابة بجلسة المستخدم (RLS يحكم). **لا `service_role` بالمتصفح.**

## 1) الدخول والصلاحيات
- دخول بالهاتف + PIN من 6 أرقام (نفس Supabase Auth وحسابات التطبيق، بلا رسائل؛ ADR 0001): `signInWithPassword(phonePinCredentials(phone, pin))`. إنشاء الحسابات: الأدمن ينشئ حساب موظف أو سائق مباشرة (`admin-create-user`، §2.6)، أو يرقّي حساباً سجّل من التطبيق (`set_user_role`). خطأ `invalid_credentials` ← "الرقم أو الرمز غير صحيح"، و429 ← "محاولات كثيرة، انتظر قليلاً".
- `src/proxy.ts` (اسم `middleware.ts` منذ Next 16): لا جلسة ← `/login` (مع `?next=`). الدور ليس `admin` أو `staff` أو الحساب معطّل ← صفحة "غير مصرح". الموظف على صفحة أدمن ← "غير مصرح" (403) حتى بالرابط المباشر. الصفحات العامة `/privacy` و`/terms` و`/delete-account` بلا دخول.
- صفحة البداية للدورين: الرئيسية `/` (الموظف يراها **بلا أي مبالغ**، §2.0).
- القائمة الجانبية (يمين) بترتيب التصميم المعتمد: الرئيسية، الطلبات (شارة الطلبات الجديدة)، المنتجات والمخزون، هدر اليوم، التقييمات، التقارير والأرباح، الإعدادات والموظفون (تحتها: الموظفون والسائقون `/staff`، العناوين `/addresses`). للموظف: الرئيسية، الطلبات، المخزون (`/stock`)، التقييمات. مصدر واحد: `apps/admin/src/lib/access.ts`.
- القائمة الجانبية تخفي ما لا يخص `staff` (المنتجات، التكاليف والمبالغ، الأرباح، الهدر والحركات، العناوين، الموظفين، الإعدادات). الحماية الحقيقية في RLS والدوال (المبالغ لا تُرجَع للموظف أصلاً)، والإخفاء للراحة فقط.

| الصفحة | admin | staff |
|---|---|---|
| الرئيسية (مؤشرات اليوم) | ✓ | ✓ بلا مبالغ |
| الطلبات | ✓ | ✓ |
| المخزون (الأرصدة وتنبيه النقص) | ✓ | ✓ |
| المخزون (حركات، هدر اليوم، حد النقص) | ✓ | ✗ |
| التقييمات | ✓ | ✓ |
| المنتجات والأقسام | ✓ | ✗ |
| العناوين (قطاعات/وحدات/عمارات) | ✓ | ✗ |
| التقارير والأرباح | ✓ | ✗ |
| الموظفون والسائقون | ✓ | ✗ |
| الإعدادات | ✓ | ✗ |

## 2) الصفحات

### 2.0 الرئيسية (مؤشرات اليوم)
- **المصدر:** دالة واحدة `dashboard_today()` (SPEC-backend §12)، بتوقيت بغداد. للموظف ترجع الأعداد فقط (حقول المبالغ `null`)، فلا تُعرض بطاقات المبالغ له.
- **بطاقات اليوم:**
  - **المبيعات** (أدمن): مجموع `subtotal` للطلبات المسلّمة اليوم حسب `delivered_at`، بدون أجرة التوصيل (تروح للسواق).
  - **الطلبات المكتملة** (المسلّمة اليوم حسب `delivered_at`) و**الملغاة** (حسب `cancelled_at`).
  - **الطلبات الواردة اليوم** (حسب `created_at`، أي حالة): عدد منفصل.
  - **صافي الربح** (أدمن): الربح الإجمالي ناقص كلفة الهدر ناقص كلفة تسويات الجرد السالبة (SPEC-backend §2).
  - **الطلبات المفتوحة الآن** مع عدد كل حالة (`pending`، `preparing`، `ready`، `out_for_delivery`).
  - **متوسط الطلب** (أدمن)، **كلفة هدر اليوم** (أدمن)، **منتجات تحت حد النقص** (عدد ورابط للمخزون).
- **المقارنة:**
  - المبيعات والمكتملة والملغاة والواردة: مع **أمس من 00:00 حتى نفس الساعة والدقيقة الآن** (بغداد)، بنسبة تغيّر وسهم.
  - صافي الربح: مع **أمس كاملاً**.
  - لا مقارنة عند غياب بيانات أمس (يُعرض "—" لا "∞%").
- **تحت البطاقات:** طلبات اليوم بنفس مكوّن جدول الطلبات (§2.1) مع رابط للصفحة الكاملة، وتحديث Realtime كصفحة الطلبات.
- **قواعد العرض:**
  - الرقم يُعرض كاملاً ولا يُقص أبداً داخل البطاقة: البطاقة تكبر أو السطر يلتف، وأرقام بعرض ثابت (`tabular-nums`)، بلا `overflow: hidden` ولا `text-overflow`.
  - الصفحة أعرض على الشاشات الكبيرة: الحاوية تتسع حتى 1600px (لا عرض ثابت ضيق)، والبطاقات بشبكة `auto-fit`.
- التصميم: شاشة "الرئيسية" بالتصميم المعتمد (تُضاف قبل T25).

### 2.1 الطلبات
- تبويبات بالحالة مع عدادات: جديد (`pending`)، قيد التحضير، جاهز (بانتظار السائق)، بالطريق، مسلّم اليوم، ملغي.
- **Realtime:** اشتراك بـ `INSERT` على `orders` ← صوت تنبيه + إضافة للأعلى. تحديث بـ `UPDATE` للطلبات المعروضة فقط.
- جدول: الرقم، الوقت، الزبون، الوحدة والعمارة، عدد القطع، المجموع، السائق، الحالة. صفحات 50 (keyset).
- فلترة بالتاريخ، الحالة، السائق، والبحث برقم الطلب أو هاتف الزبون.
- **تفاصيل الطلب** (لوحة جانبية):
  - الزبون: الاسم والهاتف، والعنوان الكامل (`formatAddress`: قطاع ← وحدة ← عمارة ← شقة) وملاحظة العنوان، وملاحظة الطلب.
  - البنود (للتحضير) مع زر **طباعة** (صفحة طباعة بعرض 80mm لطابعة إيصالات).
  - أزرار حسب الحالة والدور: "بدء التحضير"، "جاهز" (يبلّغ كل السائقين النشطين والزبون)، "إلغاء" (يطلب سبباً؛ الموظف حتى `ready`، الأدمن أيضاً من `out_for_delivery`)، "تعيين/تغيير سائق" (من `preparing` أو `ready`؛ قائمة السائقين النشطين من `list_drivers()`، متاحة للموظف والأدمن).
  - سجل الحالات (`order_status_history`) والتقييم إن وُجد.
  - للأدمن فقط: تكلفة البنود والربح.
- الجدول مكوّن واحد يُعاد استخدامه بالرئيسية (طلبات اليوم).
- **التبويبات والفلاتر (T17):** المفتوحة (جديد، قيد التحضير، جاهز، بالطريق) تعرض كل المفتوح الآن؛ "مسلّم" و"ملغي" ليوم بغداد (اليوم افتراضياً) حسب `delivered_at`/`cancelled_at`. اختيار يوم بالتبويبات المفتوحة يفلتر `created_at`. **البحث** (رقم طلب بـ # اختياري، أو هاتف بأي صيغة ← `customer_phone`) يتجاوز التبويب واليوم ويبقي فلتر السائق. الحالة بالرابط (`?tab=&day=&driver=&q=&order=`). سبب الإلغاء إلزامي (≤ 300). الإيصال `/print/orders/<id>` بعرض 80mm بلا كلفة.

### 2.2 المنتجات والأقسام (أدمن)
- جدول منتجات: صورة مصغرة، الاسم، القسم، وحدة البيع، سعر البيع، **سعر الشراء** (آخر سعر مشتريات)، هامش الربح %، الرصيد، حد النقص، نشط، الترتيب. **منتجات نص الكيلو تُعرض بالكيلو** (السعر والكلفة "/ كيلو"، الرصيد والحد بالكيلو؛ §2.9)، والباقي بوحدته ("/ باقة"، "3 حبة").
- **الكتابة عبر دوال قاعدة البيانات فقط** (لا insert/update مباشر على `products` و`product_costs`): `admin_save_product` (إنشاء/تعديل كل الحقول مع سعر الشراء وحد النقص بمعاملة واحدة)، `set_product_price` (التعديل السريع)، `reorder_products` (الترتيب). الأقسام تبقى كتابة مباشرة للأدمن بـ RLS (لا مبالغ فيها؛ التفاصيل أدناه).
- إنشاء/تعديل: وحدة البيع **قائمة ثابتة** من `SALE_UNITS` (`نص كيلو`، `باقة`، `حبة`، `علبة`، `قنينة`، `سلة`؛ قيد `products_unit_allowed` بقاعدة البيانات، ووحدة جديدة = migration). السعر يُدخل **لكل كيلو بمضاعفات 500** لمنتجات نص الكيلو (يُحفظ لكل نص كيلو = النصف، فيبقى مضاعف 250)، ولكل وحدة بمضاعفات 250 للباقي (تحقق بالنموذج عبر المساعد المشترك §2.9 + قيد قاعدة البيانات على سعر وحدة البيع)، رفع صورة مع **تصغير بالمتصفح** (800px، WebP، < 200KB) ثم رفع لـ `product-images`.
- تعطيل بدل الحذف (الطلبات القديمة تشير للمنتج).
- تغيير الترتيب بالسحب للأقسام والمنتجات.
- **الأقسام مع صور (قرار المالك 2026-11-15):** بطاقات بقسم في صفحة المنتجات (تصميم "Products"): الصورة، الاسم، عدد المنتجات، تعديل. الأدمن يضيف ويعدّل الاسم ويرتّب بالسحب (`sort_order`) ويخفي (`is_active = false`، لا حذف لأن المنتجات تشير للقسم؛ القسم المخفي يختفي من تطبيق الزبون مع بقاء منتجاته بالقاعدة)، ويرفع **صورة لكل قسم**: نفس تصغير صور المنتجات بالمتصفح (WebP؛ 400px لأن الصورة صغيرة، < 100KB) ثم رفع لـ `product-images/categories/<category_id>/<timestamp>.webp` وحفظ المسار بـ `categories.image_path`. الكتابة على Storage للأدمن فقط (سياسات الـ bucket الحالية)، والقراءة عامة كصور المنتجات. القسم بلا صورة يعرض بديلاً (أول حرف).
- تعديل سريع للسعر من الجدول.
- تنبيه: منتجات بلا سعر شراء.

### 2.3 المخزون
- جدول (أدمن وموظف): المنتج، الرصيد الحالي، حد النقص، آخر حركة. قاعدة البيانات تخزّن الرصيد والحركات بوحدة البيع (أنصاف الكيلو للخضار والفواكه)، لكن **اللوحة تعرض وتُدخل بالكيلو** لمنتجات نص الكيلو (رصيد 20 وحدة = "10 كيلو"، خطوة 0.5) وبالوحدة للباقي، عبر المساعد المشترك (§2.9).
- **حد النقص لكل منتج** (`stock.low_stock_threshold`، افتراضي 5 وحدات بيع = 2.5 كيلو لمنتجات نص الكيلو، يعدّله الأدمن بالكيلو أو بالوحدة): الرصيد تحت الحد ← تمييز بالجدول، وفلتر "تحت الحد"، وبطاقة بالرئيسية. عند نزول منتج تحت حده (بأي حركة، ومنها البيع) يصل **إشعار واحد** للأدمن (SPEC-backend §12)، ولا يتكرر حتى يرتفع الرصيد للحد أو فوقه ثم ينزل من جديد.
- أدمن (كلها عبر دوال، ولكل حركة كلفة وحدة محفوظة معها للتاريخ):
  - **"إضافة مشتريات"** (`purchase`): الكمية (بالكيلو بخطوة 0.5 أو بالوحدة) + **سعر الشراء** (إلزامي: للكيلو بمضاعفات 500، أو للوحدة بمضاعفات 250؛ يُحفظ لكل وحدة بيع)؛ يصير سعر الشراء الحالي للمنتج (آخر سعر).
  - **"هدر اليوم"** (شاشة مستقلة، تصميم "Daily Waste"): جدول المنتجات النشطة بحقل كمية لكل منتج (بالكيلو بخطوة 0.5 أو بالباقة/الوحدة، مع تسمية الوحدة بجانب المنتج)، يُحفظ دفعة واحدة بمعاملة واحدة (`adjust_stock_bulk`)، مع ملاحظة اختيارية. يعرض كلفة الهدر قبل الحفظ.
  - **"تسوية جرد"** (`adjust`) بإشارة موجبة أو سالبة مع ملاحظة إلزامية؛ السالبة تُحسب خسارة بكلفة الوحدة.
- سجل الحركات لكل منتج (أدمن): النوع، الكمية (بالكيلو أو الوحدة)، الكلفة (للكيلو أو للوحدة)، القيمة، المستخدم، الملاحظة؛ صفحات 50، فلترة بالنوع والتاريخ.

### 2.4 العناوين (أدمن)
- شجرة: قطاعات (`قطاع A`، `قطاع B`) ← وحدات (`A1..A9`، `B1..B8`؛ جدول `subsections`) ← عمارات (`buildings`، 1..100 داخل كل وحدة). إضافة، تعديل الاسم، تعطيل، ترتيب. التسميات بالواجهة: "وحدة" و"عمارة".
- **إضافة عمارات بالجملة لوحدة:** إدخال مدى (مثلاً 1 إلى 100) أو لصق قائمة أرقام، مع معاينة قبل الحفظ وتجاهل المكرر.

### 2.5 التقارير (أدمن)
- من `daily_stats`: اختيار مدى تاريخ (اليوم، أمس، 7 أيام، الشهر، مخصص).
- بطاقات: الطلبات الواردة، المسلّمة، الملغاة، المبيعات (الإيراد بدون الأجرة)، أجور التوصيل (للسواق، للعلم)، التكلفة، الربح الإجمالي، **كلفة الهدر**، **خسارة تسويات الجرد**، **صافي الربح**، متوسط قيمة الطلب.
- رسم بياني يومي للمبيعات وصافي الربح.
- **تقرير الهدر** للمدى: لكل منتج الكمية (بالكيلو أو الوحدة، §2.9) والكلفة، مرتّب بالكلفة (`report_waste`).
- **أكثر المنتجات مبيعاً** للمدى، الكمية بالكيلو أو الوحدة (استعلام على `order_items` للطلبات المسلّمة بالمدى، حد 20، يعتمد فهرس `orders(status, created_at)`).
- أداء السائقين: عدد الطلبات المسلّمة لكل سائق بالمدى.
- متوسط التقييم وآخر التعليقات.
- تصدير CSV (الكميات بالكيلو أو الوحدة مع عمود الوحدة، كالشاشة).

### 2.6 الموظفون والسائقون (أدمن)
- قائمة المستخدمين بدور غير `customer`، وبحث بالهاتف لأي حساب (زبون أو غيره) للترقية أو إعادة ضبط الـ PIN.
- **"إضافة موظف أو سائق"** (أدمن) ← Edge Function `admin-create-user` (المواصفة أدناه): الهاتف، الاسم، الدور (`staff` أو `driver`)، ورمز مؤقت (يدوي يمر بـ `validatePin` أو "رمز عشوائي"). النجاح: الرمز يظهر **مرة واحدة** مع نسخ ورابط `wa.me` برسالة جاهزة ("حسابك بالمخضر جاهز. رمزك المؤقت: ……، غيّره من حسابي"). الرقم المسجّل مسبقاً ← رسالة "الرقم مسجّل" مع اقتراح الترقية بدل الإنشاء.
- تغيير الدور وتعطيل/تفعيل ← `set_user_role`.
- لا يمكن للأدمن تخفيض نفسه.

#### إعادة ضبط رمز الدخول (PIN) — "نسيت الرمز"
لا رسائل بالنظام (ADR 0001). الزبون (أو الموظف/السائق) يراسل المتجر على **واتساب من نفس الرقم المسجّل**؛ هذا هو التحقق من الملكية.

**الواجهة (أدمن فقط):** زر "إعادة ضبط رمز الدخول" بصف المستخدم (نتيجة البحث بالهاتف) ← نافذة تعرض الاسم والرقم وتحذيراً: "تأكد أن رسالة الواتساب من نفس الرقم: 07…" ← حقل PIN جديد (6 أرقام، `validatePin(pin, phone)` بالمتصفح) أو زر "رمز عشوائي" (يولّد رمزاً يمر بـ `validatePin`) ← تأكيد ← نجاح: الرمز يظهر **مرة واحدة** مع زر نسخ ورابط `https://wa.me/<الرقم>?text=...` برسالة جاهزة للزبون ("رمز دخولك الجديد: ……، غيّره من حسابي"). لا يُخزن الرمز ولا يُسجل بأي مكان.

**Edge Function `admin-reset-pin`** (مواصفة الآن؛ تُبنى بـ T19، مع migration جديدة):
- `POST /functions/v1/admin-reset-pin`، `Authorization: Bearer <JWT الأدمن>`، `verify_jwt = true`. الجسم: `{ "user_id": "<uuid>", "new_pin": "######" }`.
- الخطوات بالترتيب:
  1. `auth.getUser(jwt)` ← المستدعي؛ ملفه `role = 'admin'` و`is_active`، وإلا `NOT_ALLOWED` (403). بلا JWT صالح: `NOT_AUTHENTICATED` (401).
  2. `user_id` uuid صالح؛ الملف موجود، وإلا `USER_NOT_FOUND` (404).
  3. الهدف ليس `admin` (ولا المستدعي نفسه)، وإلا `ADMIN_ACCOUNT` (403). رمز الأدمن يغيّره صاحبه من حسابي، أو صاحب المشروع بـ SQL (RUNBOOK §7). يمنع أدمن مخترَقاً من أخذ حسابات الأدمن الآخرين.
  4. `new_pin` بعد `normalizePin`: 6 أرقام وغير سهل ولا من رقم الهدف (نفس قواعد `validatePin`، منسوخة للدالة مع اختبار تطابق)، وإلا `PIN_INVALID` (400، `detail` = `PIN_LENGTH` / `PIN_TRIVIAL` / `PIN_MATCHES_PHONE`).
  5. حد: 20 إعادة ضبط لكل أدمن بالساعة (من سجل التدقيق)، وإلا `TOO_MANY_RESETS` (429).
  6. `auth.admin.updateUserById(user_id, { password: pin })` بمفتاح `service_role` (داخل الدالة فقط).
  7. إبطال كل جلسات الهدف: دالة SQL جديدة للـ `service_role` فقط (`revoke_user_sessions(p_user_id)` تحذف صفوف `auth.sessions`، فتسقط رموز التحديث). رمز الوصول الحالي يبقى صالحاً حتى انتهائه (≤ ساعة).
  8. سجل تدقيق: جدول جديد `pin_resets (id, user_id, reset_by, created_at)` يقرأه الأدمن فقط (RLS)، بلا الرمز.
  9. الرد `200 { "ok": true }`. الرمز لا يرجع ولا يُكتب بالسجلات (لا `console.log` للجسم).
- أي خطأ بالخطوات 6–8 ← `500 { "error": "INTERNAL" }`، والرسالة بالواجهة عامة. الرموز الجديدة (`PIN_INVALID`، `TOO_MANY_RESETS`) تُضاف لـ `packages/shared/errors.ts` وSPEC-backend §5 مع البناء (T19)، وتُقرأ بـ `parseFunctionError`.
- الاختبارات (T19): `deno test` بـ fetch مزيف (غير أدمن ← 403، هدف أدمن ← 403، رمز سهل ← 400، نجاح يستدعي updateUserById وإبطال الجلسات ويكتب السجل، الحد 20/ساعة)؛ pgTAP لـ `revoke_user_sessions` وصلاحياته وRLS `pin_resets`؛ تكامل على dev: بعد إعادة الضبط يفشل الرمز القديم وينجح الجديد ويسقط رمز التحديث القديم.

#### إنشاء حساب موظف أو سائق — `admin-create-user` (مواصفة؛ تُبنى بـ T19)
- `POST /functions/v1/admin-create-user`، `Authorization: Bearer <JWT الأدمن>`، `verify_jwt = true`. الجسم: `{ "phone": "07…", "full_name": "…", "role": "staff" | "driver", "pin": "######" }`.
- الخطوات: المستدعي أدمن نشط (وإلا 401/403 كـ `admin-reset-pin`)؛ `normalizeIraqiPhone` وإلا رقم غير صالح (400)؛ الدور `staff` أو `driver` فقط (لا `admin` ولا `customer`، 400)؛ `validatePin(pin, phone)` وإلا رمز غير صالح (400 مع السبب)؛ حد 20 إنشاء لكل أدمن بالساعة (429)؛ `auth.admin.createUser({ phone, password: pin, phone_confirm: true })` بـ `service_role` داخل الدالة (رقم موجود ← 409 "الرقم مسجّل")؛ ثم بمعاملة: الاسم والدور على `profiles` وسجل تدقيق `user_creations (id, user_id, created_by, role, created_at)` يقرأه الأدمن فقط. فشل بعد الإنشاء ← حذف الحساب المُنشأ و500.
- الرد `201 { "user_id": "…" }`. الرمز لا يرجع ولا يُسجَّل. الموظف يغيّر رمزه بعد أول دخول (تطبيق أو لوحة، "تغيير الرمز" يسجّل الدخول أولاً، ADR 0001).
- رموز الأخطاء تُضاف لـ `packages/shared/errors.ts` وSPEC-backend §8 مع البناء (T19)، وتعيد استخدام رموز `signup` و`admin-reset-pin` حيث تنطبق.
- الاختبارات (T19): `deno test` بـ fetch مزيف (غير أدمن، دور ممنوع، رمز سهل، رقم مكرر، الحد، نجاح يكتب الدور والسجل)؛ pgTAP لـ RLS `user_creations`؛ تكامل على dev: الحساب الجديد يدخل بالرمز المؤقت وبدوره.

### 2.7 الإعدادات (أدمن)
- أجرة التوصيل (مضاعفات 250)، الحد الأدنى للطلب (مضاعفات 250، قيد بقاعدة البيانات أيضاً)، حد الطلبات المفتوحة للزبون (افتراضي 3)، فتح/غلق المتجر + رسالة الإغلاق.
- **الحفظ عبر دالة** `update_app_settings` (لا update مباشر على `app_settings`).
- حالة الإشعارات: عدد الإشعارات غير المرسلة الأقدم من 5 دقائق (تنبيه إن كان > 0).

### 2.8 التقييمات (أدمن وموظف)
- رأس الصفحة: **المتوسط العام** (رقم عشري واحد) مع **عدد التقييمات** و**توزيع النجوم** 1..5، من `ratings_summary(from?, to?)` (SPEC-backend §12).
- قائمة بصفحات 50 (keyset على `created_at`، `order_id`): النجوم، التعليق كاملاً، رقم الطلب (رابط لتفاصيله)، اسم الزبون، التاريخ.
- فلترة بالنجوم (مثلاً 1–2 فقط) وبالمدى الزمني (يُطبَّق على المتوسط والقائمة معاً).
- التصميم: شاشة "التقييمات" بالتصميم المعتمد (تُضاف قبل T26).

### 2.9 الكميات والأسعار بالكيلو (كل اللوحة؛ قرار المالك 2026-11-15)
- **داخل اللوحة** كل كمية لمنتج وحدته `نص كيلو` تُعرض وتُدخل **بالكيلو** بخطوة 0.5: الرصيد، المشتريات، الهدر، تسويات الجرد، حد النقص، سجل الحركات، التقارير (الهدر، أكثر المنتجات مبيعاً، CSV)، وقائمة النقص بالرئيسية. وكل سعر بيع وسعر شراء له يُعرض ويُدخل **لكل كيلو**.
- **سعر الكيلو مضاعف 500** حتى يبقى سعر نص الكيلو مضاعف 250 (قيد قاعدة البيانات). سعر كيلو 1250 مرفوض بالنموذج برسالة واضحة.
- **الباقة والحبة وباقي الوحدات** تبقى بوحدتها (عدد صحيح، السعر للوحدة بمضاعفات 250).
- **قاعدة البيانات لا تتغير:** تخزّن وحدات البيع (أنصاف الكيلو) والسعر لكل وحدة بيع. التحويل في **مساعد واحد مشترك** `packages/shared/src/adminUnits.ts` (باختبارات)، ولا تحويل مكتوب داخل الصفحات:
  - `isKiloProduct(unit)`؛ `kgToUnits(kg)` (يقبل السالب للتسويات، ويرفض غير مضاعفات 0.5) و`unitsToKg(units)`.
  - `perKgToUnitPrice(perKg)` (يرفض غير مضاعفات 500) و`unitPriceToPerKg(price)`؛ `isValidPerKgPrice`.
  - دوال عامة حسب الوحدة: `toAdminQty`/`fromAdminQty`، `toAdminPrice`/`fromAdminPrice` (تحويل لنص الكيلو، تمرير كما هو للباقي)، `adminUnitLabel(unit)` ("كيلو" أو اسم الوحدة)، و`formatAdminQuantity(units, unit)` ("10.5 كيلو"، "0 كيلو"، "3 باقة"؛ يقبل الصفر بخلاف `formatQuantity`).
- بنود الطلب (تفاصيل الطلب والطباعة) تبقى بـ `formatQuantity` ("نص كيلو"، "1.5 كيلو") كما يراها الزبون.
- **تطبيق الزبون لا يتغير:** يعرض السعر لكل نص كيلو والكمية بـ `formatQuantity`.

## 3) الأداء
- كل الجداول بصفحات (50) وفلترة على الخادم. لا تحميل لكل الطلبات.
- التقارير من `daily_stats`؛ فقط "أكثر المنتجات مبيعاً" و"أداء السائقين" و"تقرير الهدر" و"الطلبات الواردة" استعلامات مباشرة محدودة بمدى التاريخ (عبر دوال، بفهارس).
- الرئيسية: استدعاء واحد لـ `dashboard_today()` (لا عدة استعلامات من المتصفح)، ويُعاد عند أي تغيير Realtime مع تأخير قصير (debounce).
- Server Components للقراءة الأولية، وTanStack Query للتحديث.

## 4) الاختبارات
- **Playwright (ضد Supabase محلي + seed):**
  - أدمن: دخول (هاتف + PIN بمستخدم العرض و`DEMO_PIN`)، إعادة ضبط PIN زبون، إنشاء حساب سائق (T19)، إنشاء منتج بصورة (سعر بالكيلو يُحفظ نصفه لنص الكيلو)، قسم جديد بصورة وإخفاؤه، تعديل سعر، مشتريات بسعر شراء، هدر اليوم، بدء تحضير طلب، تعيين سائق، رؤية التقرير والرئيسية والتقييمات.
  - staff: لا يرى صفحات الأدمن، ولا يصل لها بالرابط المباشر، ويقدر يحضّر ويلغي؛ الرئيسية بلا مبالغ (لا رقم بالدينار بالصفحة)؛ يرى المخزون والتقييمات.
  - زبون يحاول فتح اللوحة ← "غير مصرح".
- **وحدة:** مساعد الكيلو `adminUnits` (بـ `packages/shared`: كيلو ↔ وحدات، سعر الكيلو ↔ سعر نص الكيلو، رفض سعر كيلو غير مضاعف 500 وكمية غير مضاعف 0.5، تمرير الباقة والحبة كما هي)، تحقق السعر (مضاعف 250 للوحدة، 500 للكيلو)، تصغير الصورة، تحليل مدى العمارات، مولّد الـ PIN العشوائي يمر بـ `validatePin`، حساب نسبة التغيّر (أمس صفر ← "—")، تنسيق الأرقام الكبيرة بلا قص.

## افتراضات
1. اللوحة على Vercel (الخطة المجانية تكفي للبداية)، مع نطاق فرعي مثل `admin.<domain>`.
2. صفحات سياسة الخصوصية والشروط وحذف الحساب (للويب، مطلوبة من Google) ضمن نفس مشروع Next.js كصفحات عامة.
3. الطباعة عبر نافذة طباعة المتصفح (لا تكامل مباشر مع طابعة).
4. ~~حد الرصيد المنخفض ثابت (5)~~ ← **قرار المالك 2026-11-15:** حد لكل منتج (افتراضي 5 وحدات بيع، يعدّله الأدمن)، تنبيه مرئي بالرئيسية والمخزون، وإشعار واحد للأدمن عند النزول تحت الحد.

6. تعديل بنود طلب قائم غير مدعوم: الحل إلغاء الطلب وطلب جديد من الزبون.
7. **الدخول بالهاتف + PIN (قرار المالك 2026-11-14، ADR 0001):** نفس طريقة التطبيق للأدمن والموظفين. إعادة ضبط الـ PIN للأدمن فقط وعبر `admin-reset-pin`؛ لا تُعاد لحساب أدمن من اللوحة. سجل `pin_resets` استثناء من افتراض 5 (تدقيق إعادة الضبط مطلوب لأنه يمنح دخولاً لحساب).
8. **قرارات المالك 2026-11-15 (لوحة مماثلة بوظائفها لمشروع سابق، بلا نسخ تصميمه):**
   - **المبيعات** = مجموع `subtotal` للطلبات المسلّمة بدون أجرة التوصيل، بتاريخ `delivered_at` (بغداد). "الطلبات الواردة اليوم" عدد منفصل حسب `created_at`.
   - **صافي الربح** = الربح الإجمالي − كلفة الهدر − كلفة تسويات الجرد السالبة، بكلفة الوحدة المحفوظة على الحركة. لا جدول مصاريف تشغيل الآن (خيار لاحق).
   - **سعر الشراء** يُسجَّل مع كل حركة مشتريات، و`product_costs` = آخر سعر مشتريات. الحركات تحتفظ بكلفتها للتاريخ.
   - **إنشاء الحسابات:** `admin-create-user` (أدمن فقط) إلى جانب الترقية وإعادة الضبط.
   - **الموظف** يرى: الطلبات، المخزون، التقييمات، والرئيسية بلا أي مبالغ.
   - **كتابة المنتجات والأسعار والإعدادات** عبر دوال قاعدة البيانات فقط.
   - **التصميم:** شاشات الرئيسية والتقييمات وهدر اليوم تُضاف للتصميم المعتمد قبل T25/T26 (وT18 لهدر اليوم).
